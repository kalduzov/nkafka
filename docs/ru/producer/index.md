# Продюсеры

[English](../../en/producer/index.md)

## Статус транзакционного интерфейса

Транзакционный интерфейс проектируется в рамках [KIP-98](../../../spec/KIP/KIP-98/README.md). Ниже описан целевой контракт и правила его использования. Пример использует проектируемые методы и пока не является запускаемым примером текущей версии библиотеки.

## Транзакционная конфигурация

Проектируемый `TransactionalProducerConfig` наследует `ProducerConfig`, сохраняя принятую в библиотеке иерархию конфигураций. Общие параметры отправки наследуются; `TransactionalId` и `TransactionTimeoutMs` принадлежат транзакционной конфигурации.

Транзакционная конфигурация задаёт корректные начальные значения, включая `EnableIdempotence = true` и `Acks = Acks.All`. Унаследованные свойства доступны для изменения, но несовместимые изменения пользователя приводят к `KafkaConfigException` на этапе валидации, до сетевой инициализации. Исключение указывает ошибочный параметр; библиотека не исправляет его молча.

Валидатор выполняет базовые проверки конфигурации, затем транзакционные проверки итоговых настроек. Прямое создание и все методы расширения используют одну цепочку валидации, включая конфигурации, заданные через пользовательскую функцию настройки. Способ копирования для создания производных конфигураций из общей базовой ещё уточняется в KIP-98.

Если перегрузка получает явный ID и конфигурацию, отсутствующий ID (`null` или пустая строка) заполняется из аргумента, а совпадающий допускается. Непустой отличающийся ID приводит к `KafkaConfigException` до резервирования ID и сетевой инициализации. Сравнение порядковое, с учётом регистра, без обрезки пробелов. Переданная конфигурация не изменяется. После пользовательской функции настройки выполняется та же проверка; явный аргумент сам должен быть допустимым непустым ID.

## Повторное использование транзакционных ID

Внутри одного `IKafkaCluster` запрещено создавать второй активный транзакционный продюсер с тем же `TransactionalId`. ID резервируется атомарно после валидации и до сетевой инициализации. Повторное создание, в том числе одновременное, приводит к исключению без инициализации второго продюсера и без изменения первого экземпляра. Существующий продюсер не возвращается.

Резервирование сохраняется между транзакциями и во время закрытия. При ошибке или отмене создания ID освобождается только после очистки частично созданных ресурсов; при обычном освобождении — только после полного завершения работы. Неисправный продюсер продолжает занимать свой ID до освобождения. Перед созданием замены полностью освободите предыдущий экземпляр.

Проверка действует только внутри одного объекта кластера. Другой объект кластера или процесс может использовать тот же ID и вытеснить предыдущий продюсер на стороне Kafka.

## Время жизни транзакционного продюсера

**Не регистрируйте транзакционный продюсер как общий `singleton` в контейнере зависимостей. Управляйте его созданием, использованием и асинхронным освобождением явно из кода.** Это правило относится к любому контейнеру, предоставляющему один экземпляр нескольким независимым получателям.

У одного транзакционного продюсера может быть только одна незавершённая транзакция. Регистрация как `singleton` не сериализует вызовы и не создаёт отдельное транзакционное состояние для каждого получателя. Даже возможность параллельно отправлять сообщения внутри одной транзакции не означает поддержку нескольких независимых транзакций на одном продюсере.

При общем использовании возникают следующие проблемы:

- **Конфликт обработчиков.** Пока один обработчик выполняет транзакцию, другой не сможет начать свою и получит ошибку состояния. Автоматическое повторение без координации не решает вопрос владения.
- **Общая область отказа.** Вытеснение продюсера другим экземпляром с тем же `TransactionalId`, окончательная ошибка или неопределённый исход завершения могут сделать экземпляр непригодным для дальнейшей работы всех получателей.
- **Конфликт освобождения.** Один получатель может закрыть экземпляр, которым ещё пользуются другие. Если все полагаются только на освобождение контейнером, завершение активной обработки может не быть согласовано с закрытием продюсера и кластера.
- **Сложное восстановление.** После замены неисправного экземпляра ранее полученные ссылки продолжают указывать на старый. Контейнер сам по себе не обеспечивает безопасный перевод обработчиков на новый экземпляр.
- **Отсутствие изоляции между процессами.** Регистрация `singleton` действует внутри контейнера. Другой процесс с тем же `TransactionalId` может вытеснить этот продюсер на стороне Kafka.

Отдельный `IProducerTransaction` делает принадлежность сообщений явной: библиотека не должна молча включать отправки независимого обработчика в чужую транзакцию. Основной риск общего продюсера — конфликт управления и общая область отказа, а не обещанная поддержка независимых транзакций.

## Рекомендуемая организация

Назначьте экземпляру одного владельца — например, последовательный фоновый обработчик. Владелец создаёт продюсер, выполняет транзакции по очереди и освобождает его после завершения обработки. При неисправности он прекращает использование экземпляра и явно управляет восстановлением.

Долго живущий продюсер допустим: создавать новый на каждое сообщение или транзакцию не требуется. Ограничение касается передачи одного экземпляра независимым получателям через контейнер. Сам фоновый обработчик может управляться контейнером, но транзакционным продюсером внутри него владеет его код.

Для независимых параллельных обработчиков нужны отдельные продюсеры с различными `TransactionalId`. Простая замена регистрации `singleton` на другую длительность жизни не решает задачу, если новые экземпляры получают одинаковый ID.

```csharp
// cluster уже открыт и живёт дольше продюсера.
await using var producer = await cluster.CreateTransactionalProducerAsync(
    new TransactionalProducerConfig
    {
        TransactionalId = "orders-worker-0"
    },
    cancellationToken);

await foreach (var message in messages.WithCancellation(cancellationToken))
{
    await using var transaction =
        await producer.BeginTransactionAsync(cancellationToken);

    await transaction.ProduceAsync("orders", message, cancellationToken);
    await transaction.CommitAsync(cancellationToken);
}
```

Здесь `messages` — поток подготовленных приложением сообщений; пример не описывает подтверждение смещений потребителя Kafka. Продюсер создаётся один раз на время работы владельца, а объекты транзакций — последовательно внутри цикла.

При остановке сначала прекращается новая обработка, затем завершается активная транзакция по правилам её состояния, освобождается продюсер и только после этого кластер. Истечение времени ожидания подтверждения не означает гарантированную отмену: нельзя автоматически повторять бизнес-операцию или переключаться на отмену при неизвестном исходе подтверждения. Политика ошибок и ограниченного освобождения уточняется в [общем замысле транзакционного продюсера](../../../spec/KIP/KIP-98/vision.md).

## Асинхронное освобождение и таймаут

Проектируемый интерфейс продюсеров использует только `DisposeAsync`, без синхронного `IDisposable` и отдельного `CloseAsync` с отменой. Новая общая настройка с предложенным именем `ClientDisposeTimeoutMs` ограничивает освобождение клиента. Предложенное значение по умолчанию — 5000 мс; имя, значение и допустимый диапазон ещё требуют согласования. Это проектируемый контракт, а не реализованная настройка.

Освобождение запрещает новые операции и использует единый срок для завершения работы и остановки собственных фоновых операций клиента. Запросы, повторы и вложенное освобождение транзакции не получают новый полный таймаут. При отдельном освобождении активной транзакции используется тот же параметр из конфигурации владельца.

При истечении срока клиент прекращает ожидание брокера, завершает ожидающие операции с ошибкой или неизвестным исходом и выполняет необходимую локальную очистку без дополнительного периода ожидания брокера. Возобновление работы невозможно. Планирование задач средой выполнения не позволяет гарантировать точность жёсткого реального времени, но зависшие операции не должны превращать освобождение в бесконечное ожидание.

Локальное освобождение не гарантирует, что Kafka отменила транзакцию или что сообщения не были записаны. Общие соединения кластера сохраняются для других клиентов. `CloseConnectionTimeoutMs` по-прежнему отвечает за закрытие физического соединения, а `TransactionTimeoutMs` имеет отдельное назначение. Общий контракт продюсера, потребителя и административного клиента описан в [руководстве о времени жизни клиентов](../client-lifetime.md). Конкретное исключение истечения срока и сохранение первоначального исключения приложения ещё проектируются.
