# Шаг 01. Публичные интерфейсы продюсеров

## Статус и цель

Статус: черновик для обсуждения. Исходный код этим шагом пока не изменяется.

Цель — согласовать состав публичных типов, сигнатуры, разделение конфигураций, способы создания и примеры использования обычного и транзакционного продюсеров. Согласованные решения отмечены явно; остальные формы являются предложениями. Документ не описывает уже доступные возможности библиотеки.

Подробное поведение отправки, состояния транзакции, восстановление, сетевое взаимодействие, освобождение ресурсов и смещения вынесены в [общий замысел](vision.md). Они уточняются в последующих шагах [плана KIP-98](README.md) и не входят в согласование состава интерфейсов на текущем этапе.

## 1. Разделение ответственности

| Тип | Ответственность | Чего в нём нет |
|---|---|---|
| `IKafkaCluster` | Создание клиентов и владение общими сетевыми ресурсами | Состояния отдельной транзакции |
| `IProducer` | Обычная отправка и ожидание завершения принятых сообщений | Транзакционных методов и `TransactionalId` |
| `ITransactionalProducer` | Создание последовательных транзакций одного продюсера | Отправки сообщений вне объекта транзакции |
| `IProducerTransaction` | Отправка сообщений, включение смещений, подтверждение и отмена одной транзакции | Создания вложенной или независимой транзакции |

Предложение: `ITransactionalProducer` не наследует `IProducer`; `IProducerTransaction` также не наследует `IProducer`. Общий публичный базовый интерфейс ради одинаковой сигнатуры отправки не вводится.

Обычный продюсер не означает отказ от идемпотентности. Наличие транзакции и защита повторной отправки от дубликатов — разные возможности.

Принятое решение: принадлежность отправки транзакции выражается объектом `IProducerTransaction`. Через `ITransactionalProducer` отправлять сообщения нельзя. Объект транзакции можно явно передавать прикладным методам.

Это осознанное отличие от интерфейсов Java KafkaProducer и librdkafka, в которых текущая транзакция хранится в продюсере. Явный объект выбран, чтобы случайная отправка через общий продюсер не включалась в чужую транзакцию. Такое разделение не создаёт возможности нескольких одновременных транзакций на одном продюсере.

## 2. Предлагаемые интерфейсы

Это фрагменты будущего контракта, а не готовые изменения исходного кода. Пространство имён для трёх интерфейсов — `NKafka.Clients.Producer`. Используются существующие `Message`, `TopicPartition`, `TopicPartitionOffset`, `MessageDeliveryResult` и `ConsumerGroupMetadata`; окончательный состав данных и ошибок определяется в шаге 02 до переноса интерфейсов в код.

```csharp
public interface IProducer : IAsyncDisposable
{
    Task<MessageDeliveryResult> ProduceAsync(
        TopicPartition topicPartition,
        Message message,
        CancellationToken cancellationToken = default);

    Task FlushAsync(CancellationToken cancellationToken = default);
}

public interface ITransactionalProducer : IAsyncDisposable
{
    ValueTask<IProducerTransaction> BeginTransactionAsync(
        CancellationToken cancellationToken = default);
}

public interface IProducerTransaction : IAsyncDisposable
{
    Task<MessageDeliveryResult> ProduceAsync(
        TopicPartition topicPartition,
        Message message,
        CancellationToken cancellationToken = default);

    Task SendOffsetsAsync(
        IReadOnlyCollection<TopicPartitionOffset> offsets,
        ConsumerGroupMetadata groupMetadata,
        CancellationToken cancellationToken = default);

    Task CommitAsync(CancellationToken cancellationToken = default);

    Task AbortAsync(CancellationToken cancellationToken = default);
}
```

Для отправки по имени темы предлагаются две перегрузки в виде методов расширения: `ProduceAsync(this IProducer, string, Message, CancellationToken = default)` и такой же метод для `IProducerTransaction`. Они передают `Partition.Any` в основной метод. Выбор раздела выполняет библиотека.

Обоснование формы:

- `Task` у отправки представляет окончательный результат отдельной операции и позволяет запускать несколько отправок до ожидания результатов.
- `ValueTask` у начала транзакции допускает завершение без сетевого ожидания; это выбор формы контракта, а не обещание отсутствия ввода-вывода.
- Продюсерами и объектом транзакции владеет вызывающий код. Согласовано оставить только `DisposeAsync`, без синхронного освобождения и отдельного `CloseAsync`. Предел освобождения задаётся новой общей опцией; предложенное имя — `ClientDisposeTimeoutMs`. Её полное описание вынесено в [общий замысел](vision.md).
- `FlushAsync` оставляется только обычному продюсеру. Для транзакции необходимые отправки дожидаются внутри `CommitAsync`; отдельное ожидание отправки не должно восприниматься как подтверждение транзакции.
- Методы с обработчиком доставки и массовые перегрузки пока не входят в минимальный контракт. Их необходимость обсуждается отдельно до его принятия; упрощение не должно вынуждать ждать каждое сообщение последовательно.

## 3. Получение продюсера и разделение настроек

### 3.1. Базовые методы кластера

```csharp
IProducer CreateProducer(ProducerConfig config);

Task<ITransactionalProducer> CreateTransactionalProducerAsync(
    TransactionalProducerConfig config,
    CancellationToken cancellationToken = default);
```

Согласовано: реестр экземпляров по `TransactionalId` не создаётся. `CreateTransactionalProducerAsync` создаёт новый экземпляр, а не возвращает ранее созданный. Вызывающий код явно передаёт этот экземпляр своим обработчикам и отвечает за его освобождение.

Согласованная асинхронность сохраняется: сетевая инициализация полностью завершается до возврата готового экземпляра пользователю. Метод возвращает `Task<ITransactionalProducer>`; он не открывает транзакцию. Отдельного публичного `InitTransactionsAsync` и ленивой инициализации при первом `BeginTransactionAsync` нет.

Обычный `CreateProducer` также предложен как создание нового экземпляра с владением у вызывающего кода. Его создание проверяет настройки без скрытого сетевого ожидания.

### 3.2. Две конфигурации

Согласовано разделение публичных типов:

| Тип | Назначение |
|---|---|
| `ProducerConfig` | Настройки обычной отправки; без `TransactionalId` и срока транзакции |
| `TransactionalProducerConfig` | Настройки транзакционного продюсера, включая `TransactionalId`, срок транзакции и применимые параметры отправки |

Согласовано: сохраняется принятая в проекте иерархия `CommonConfig` → `ProducerConfig` → `TransactionalProducerConfig`. Транзакционная конфигурация наследует общие параметры отправки, а `TransactionalId` и `TransactionTimeoutMs` добавляет только производный тип. Наследование конфигураций не меняет разделение интерфейсов продюсеров.

`TransactionalProducerConfig` сама устанавливает корректные начальные значения, включая `EnableIdempotence = true` и `Acks = Acks.All`. Унаследованные свойства остаются доступными пользователю. Если пользователь изменит их на несовместимые с транзакциями значения, валидатор обязан бросить исключение до сетевой инициализации. Молчаливое исправление явно заданных параметров при создании запрещено.

Ошибки итоговой конфигурации сообщаются через существующий `KafkaConfigException` с указанием параметра и причины. Ни одна перегрузка не обходит валидацию. Полный набор ограничений и правила копирования определяются в шаге 02; [общий замысел](vision.md) сохраняет требования к реализации валидаторов.

Для примеров перегрузок ниже предлагается `TransactionalProducerConfig` в форме `record` с изменяемыми свойствами. `TransactionalId` имеет начальное значение `string.Empty`, а не модификатор `required`: это позволяет передать ID отдельным аргументом, не дублируя его при создании конфигурации. Базовый метод всегда проверяет итоговый ID до начала сетевой инициализации; пустое значение недопустимо. `TransactionTimeoutMs` в примере — параметр срока транзакции; остальные свойства опущены.

### 3.3. Методы расширения с явным ID

Основной интерфейс содержит только метод с полной `TransactionalProducerConfig`. Методы расширения находятся в `NKafka.TransactionalProducerExtensions` и только формируют конфигурацию, проверяют собственные аргументы и вызывают базовый метод. Они не содержат собственной сетевой инициализации.

Предлагаются три формы:

```csharp
public static Task<ITransactionalProducer> CreateTransactionalProducerAsync(
    this IKafkaCluster cluster,
    string transactionalId,
    CancellationToken cancellationToken = default);

public static Task<ITransactionalProducer> CreateTransactionalProducerAsync(
    this IKafkaCluster cluster,
    string transactionalId,
    TransactionalProducerConfig config,
    CancellationToken cancellationToken = default);

public static Task<ITransactionalProducer> CreateTransactionalProducerAsync(
    this IKafkaCluster cluster,
    string transactionalId,
    Action<TransactionalProducerConfig> configure,
    CancellationToken cancellationToken = default);
```

Это описание будущих методов, а не реализация в библиотеке. XML-комментарии при переносе в код обязательны по разделу «XML-документация публичного контракта».

Согласовано: если `config.TransactionalId` отсутствует (`null` или пустая строка) либо точно совпадает с явно переданным `transactionalId`, используется явный ID. Непустой отличающийся ID вызывает `KafkaConfigException` до вызова базового метода, резервирования ID и сетевой инициализации. Сравнение порядковое, с учётом регистра, без обрезки пробелов. Исходный объект `config` не изменяется. Функция настройки вызывается один раз, затем её результат проходит ту же проверку совпадения ID. Её исключение также передаётся вызывающему коду без создания продюсера. Явный ID в любом случае должен пройти собственную проверку непустого значения.

Последующие изменения исходной конфигурации не должны менять работающий продюсер; механизм копирования рассматривается отдельно.

Примеры всех способов получения:

```csharp
await using var producer = await cluster.CreateTransactionalProducerAsync(
    "orders-worker-0", cancellationToken);

await using var configuredProducer = await cluster.CreateTransactionalProducerAsync(
    "audit-worker-0",
    new TransactionalProducerConfig { TransactionTimeoutMs = 30_000 },
    cancellationToken);

await using var otherProducer = await cluster.CreateTransactionalProducerAsync(
    "notifications-worker-0",
    config => config.TransactionTimeoutMs = 30_000,
    cancellationToken);

await using var directProducer = await cluster.CreateTransactionalProducerAsync(
    new TransactionalProducerConfig { TransactionalId = "export-worker-0" },
    cancellationToken);
```

Формы с готовой конфигурацией и функцией настройки являются предложенными удобными перегрузками. Для токена без дополнительных настроек используется именованный аргумент `cancellationToken`, если литерал `default` создаёт неоднозначность выбора перегрузки. Передача нетипизированного `null` вместо конфигурации или функции также неоднозначна; проверка `null` относится к уже выбранной перегрузке.

### 3.4. Минимальные правила использования интерфейсов

- `TransactionalId` обозначает транзакционного продюсера, выполняющего последовательные транзакции, а не отдельную транзакцию.
- Согласовано: в пределах одного `IKafkaCluster` повторное создание с занятым `TransactionalId` запрещено. Существующий экземпляр не возвращается. Тип исключения определяется в шаге 02; подробный срок занятости ID сохранён в [общем замысле](vision.md).
- Один продюсер выполняет последовательные транзакции. Независимые одновременные транзакции требуют отдельных продюсеров.
- Продюсером и объектом транзакции владеет вызывающий код, использующий `await using`. Согласованное ограничение общей регистрации транзакционного продюсера как `singleton` обязательно отражается в XML и руководстве; обоснование сохранено в [общем замысле](vision.md).
- Успех `ProduceAsync` внутри транзакции не означает её подтверждения. Явное подтверждение выполняет `CommitAsync`; `AbortAsync` предназначен для отмены. Подробные результаты и ошибки проектируются отдельно.
- `SendOffsetsAsync` принимает следующие позиции после обработанных записей и сведения о группе. Получение этих сведений от потребителя проектируется в шаге 06.

## 4. Примеры использования

Примеры показывают предложенный интерфейс. `cluster` — уже открытый кластер; массивы сообщений подготовлены приложением. Эти примеры пока не являются запускаемыми примерами текущей библиотеки.

### Обычная отправка

```csharp
await using var producer = cluster.CreateProducer(new ProducerConfig());

var delivery = await producer.ProduceAsync(
    "orders",
    new Message(orderKey, orderBytes),
    cancellationToken);
```

### Атомарная фиксация нескольких сообщений

```csharp
await using var producer = await cluster.CreateTransactionalProducerAsync(
    new TransactionalProducerConfig
    {
        TransactionalId = "orders-worker-0"
    },
    cancellationToken);

await using var transaction =
    await producer.BeginTransactionAsync(cancellationToken);

var orderDelivery = transaction.ProduceAsync(
    "orders", new Message(orderKey, orderBytes), cancellationToken);

var auditDelivery = transaction.ProduceAsync(
    "audit", new Message(orderKey, auditBytes), cancellationToken);

await Task.WhenAll(orderDelivery, auditDelivery);
await transaction.CommitAsync(cancellationToken);
```

### Обработка прочитанной порции

Продюсер создаётся один раз и используется для последовательных транзакций. `outputs` — результаты обработки текущей порции, `nextOffsets` — следующие позиции после обработанных записей, `groupMetadata` — актуальные сведения, полученные от потребителя. Способ их получения определяется отдельно, чтобы не выдавать отсутствующий метод потребителя за готовый.

```csharp
await using var transaction =
    await producer.BeginTransactionAsync(cancellationToken);

foreach (var output in outputs)
{
    await transaction.ProduceAsync(
        "processed-orders", output, cancellationToken);
}

await transaction.SendOffsetsAsync(
    nextOffsets, groupMetadata, cancellationToken);

await transaction.CommitAsync(cancellationToken);
```

Последовательная отправка в последнем примере выбрана для краткости; для нагрузки допустимо ограниченное число одновременных отправок. Неограниченное создание задач для всей входной последовательности не предлагается как основной способ работы.

Примеры показывают успешный путь. Повтор всей обработки после любой ошибки `CommitAsync` запрещён: приложение сначала различает подтверждённую отмену, необходимость повторного ожидания и неизвестный исход.

## 5. Изменения относительно текущего интерфейса

Совместимость можно нарушать сразу. После принятия спецификации старые члены удаляются вместе с обновлением всех затронутых мест использования; переходные перегрузки не создаются.

| Сейчас | Предложено |
|---|---|
| Транзакционные методы в `IProducer` | Отдельные `ITransactionalProducer` и `IProducerTransaction` |
| `InitTransactionsAsync` | Инициализация внутри асинхронного создания |
| `BeginTransaction()` с неявной текущей транзакцией | Возвращаемый объект конкретной транзакции |
| `CommitTransactionAsync`, `AbortTransactionAsync` | `CommitAsync`, `AbortAsync` объекта транзакции |
| `SendOffsetsToTransactionAsync` | `SendOffsetsAsync` объекта транзакции |
| `BuildProducer(name, config)` с повторным использованием по имени | `CreateProducer(config)` с явным владением новым экземпляром |
| Транзакционные настройки в `ProducerConfig` | Отдельный `TransactionalProducerConfig` и перегрузки с явным ID |
| `IDisposable`, `IAsyncDisposable`, `CloseAsync` | Продюсеры и объект транзакции освобождаются асинхронно вызывающим кодом |
| Обязательный токен отмены | Значение `default` по умолчанию |
| Внутреннее `Name` в публичном интерфейсе | Учёт клиентов внутри реализации кластера |

При переносе в код требуется обновить `IKafkaCluster`, оба набора `ProducerExtensions`, настройки, реализацию клиентов, регистрацию в `NKafka.AspNetCore`, тестовые подмены, примеры и документацию. Изменение одних интерфейсов с оставлением несовместимых реализаций не считается завершённым шагом. В текущей работе эти файлы не меняются.

## 6. Решения по публичному интерфейсу

Согласованные решения не открываются повторно. Оставшиеся вопросы рассматриваются по одному.

| Решение | Состояние |
|---|---|
| Разделение продюсеров и отправка только через объект транзакции | Согласовано |
| Отказ от обратной совместимости | Согласовано |
| Асинхронное создание готового нового транзакционного продюсера | Согласовано |
| Реестр экземпляров с возвратом ранее созданного продюсера | Отклонено |
| Локальный запрет занятого `TransactionalId` | Согласовано |
| Разделение конфигураций, наследование `TransactionalProducerConfig : ProducerConfig` и валидация несовместимых изменений | Согласовано |
| Методы расширения с явным ID и отдельной конфигурацией | Согласовано направление; конкретные сигнатуры предложены в разделе 3 |
| Несовпадение явного ID и ID конфигурации вызывает исключение; исходная конфигурация не изменяется | Согласовано |
| Только `DisposeAsync` для продюсеров и транзакции | Согласовано |
| Подробная XML-документация, два языка руководства, ограничение общего `singleton` | Согласовано |
| Отсутствие наследования между интерфейсами продюсеров | Предложено |
| Синхронный `CreateProducer` с новым экземпляром и владением у вызывающего кода | Предложено |
| Конкретные формы методов, включая `Task` отправки и `ValueTask` начала транзакции | Предложено |
| Перегрузка с `Action<TransactionalProducerConfig>` | Предложено |
| Только отправка с возвращаемой задачей либо также обработчик доставки; массовые перегрузки | Открыто |
| Байтовые сообщения либо дополнительный типизированный интерфейс | В черновике сохранена байтовая форма; дополнительный интерфейс не включён |

Полный состав настроек, результаты и ошибки уточняются в шаге 02. Общая опция срока освобождения согласована, но её имя, диапазон и значение по умолчанию относятся к этому следующему шагу. Состояния, повторы и прочие вопросы поведения перечислены в [общем замысле](vision.md), а не в списке решений текущего этапа.

Руководства по продюсерам: [English](../../../docs/en/producer/index.md), [Русский](../../../docs/ru/producer/index.md).

Подробная XML-документация обязательна для обоих продюсеров, объекта транзакции, методов создания и расширения, настроек, результатов, исключений и значений перечислений. Она создаётся вместе с исходным кодом, а не откладывается до выпуска. Язык комментариев в библиотеке — английский, согласно правилам репозитория; пояснения в спецификациях остаются на русском.

Для каждого публичного члена описываются применимые сведения:

- `<summary>` — назначение и конкретное действие, а не повтор имени метода.
- `<param>` и `<typeparam>` — смысл, допустимые значения, ограничения и роль токена отмены.
- `<returns>` — точный момент завершения операции и гарантии результата. Для отправки отдельно различаются приём в очередь, подтверждение записи и подтверждение транзакции.
- `<exception>` — документированные типы ошибок, условия возникновения и допустимое продолжение работы. Неопределённый исход не описывается как гарантированная отмена.
- `<remarks>` — состояния, параллельные вызовы, порядок сообщений, владение данными и ресурсами, ограничения времени, последствия отмены и повторного вызова.
- `<example>` — для основных сценариев: создание, обычная отправка, транзакция, включение смещений и корректная обработка ошибок завершения.
- `<see>` и `<seealso>` — ссылки на связанные операции, настройки и типы результатов.

Для `CreateTransactionalProducerAsync` обязательно объясняются создание нового экземпляра, владение у вызывающего кода, сетевые действия при инициализации, отсутствие автоматически открытой транзакции и необходимость освобождения продюсера. Для перегрузок описываются заполнение отсутствующего ID, исключение при конфликте с явным ID, неизменность исходной конфигурации и выполнение функции настройки до создания экземпляра. Ошибки и отмена создания должны описывать освобождение частично созданных ресурсов без обещания отменить уже выполненные действия на брокере.

В XML-документации создания также описываются локальный запрет занятого `TransactionalId`, исключение повторного создания, момент освобождения ID и отсутствие защиты между разными объектами кластера или процессами.

После согласования соответствующего шага в XML-документации освобождения и общей опции срока обязательно объясняются общий срок освобождения клиента, утверждённые единицы и значение по умолчанию, очистка при истечении срока, сообщение об ошибке, отличие от `CloseConnectionTimeoutMs` и отсутствие гарантии отмены на брокере. Подробные правила освобождения и исходов операций определяются в [общем замысле и следующих шагах](vision.md); этот раздел задаёт требования к их документированию.

Для настроек указываются единицы измерения, значения по умолчанию, допустимые диапазоны и несовместимые сочетания. Для `FlushAsync`, `CommitAsync`, `AbortAsync` и `DisposeAsync` описываются граница ожидаемых операций, предел ожидания и поведение при неизвестном исходе. Унаследованное освобождение ресурсов также должно иметь доступное пользователю описание особенностей продюсера и транзакции.

Пустые теги, общие фразы вместо контракта и ссылки на отсутствующие типы недопустимы. `<inheritdoc/>` допустим в реализации, если полная документация уже есть у соответствующего публичного контракта; он не заменяет описание специфичного поведения.

В `<remarks>` интерфейса `ITransactionalProducer`, метода `CreateTransactionalProducerAsync` и его перегрузок необходимо отразить ограничение регистрации как общего `singleton`, одну активную транзакцию на экземпляр и обязанность вызывающего кода управлять временем жизни. Основной пример показывает одного владельца, последовательные транзакции и освобождение продюсера до закрытия кластера; ссылка на внешнее руководство не заменяет это описание в XML.

## Проверки и условия завершения этапа

Этап проектирования завершён, когда согласованы состав типов, сигнатуры, наследование конфигураций и формы создания, примеры соответствуют контракту, а открытые вопросы именно публичного интерфейса разрешены. Отдельно обозначены зависимости от будущих типов результатов и ошибок; это не заявление о готовности переноса интерфейсов в исходный код.

Для документационного изменения проверяются ссылки, согласованность сигнатур, статусы решений, одинаковая структура английского и русского руководств и включение документов в `NKafka.slnx`. Запуск Kafka и изменение тестов не требуются.

При последующем переносе в код нужны компилируемые примеры, проверки состава интерфейсов и перегрузок, подробная XML-документация без новых предупреждений и обновление затронутых мест использования. Проверки поведения выполняются вместе с соответствующими шагами; их перечень сохранён в [общем замысле](vision.md).
