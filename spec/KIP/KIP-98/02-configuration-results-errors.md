# Шаг 02. Настройки, данные, результаты и ошибки

Статус: согласовано, готово к реализации. Согласованные ограничения из [шага 01](01-public-interfaces.md) сохраняются. Документ определяет целевое поведение настроек, данных, результатов и ошибок; реализация выполняется отдельной работой.

## Цель и зависимости

Зависимость: публичные интерфейсы шага 01. Результат — единый контракт настроек и результатов, на который опираются обычная отправка, идемпотентность и транзакции. Новые интерфейсы продюсеров повторно не проектируются.

## Текущее состояние

В коде уже есть `TransactionalProducerConfig : ProducerConfig`, валидатор транзакционных ограничений, `MessageDeliveryResult` и `PersistenceStatus`. В `ProducerConfig.Validate()` проверяется базовая конфигурация и выбор раздела; полного набора проверок числовых параметров нет. В `CommonConfig` пока отсутствует общая опция срока освобождения клиента. `CreateTransactionalProducerAsync` копирует конфигурацию через `with` и отдельно переносит несколько общих параметров; это не полная модель независимого копирования вложенных данных.

Основание: [конфигурации](../../../src/NKafka/Config/ProducerConfig.cs), [транзакционная конфигурация](../../../src/NKafka/Config/TransactionalProducerConfig.cs), [создание клиентов](../../../src/NKafka/KafkaCluster.cs), [результат отправки](../../../src/NKafka/Clients/Producer/MessageDeliveryResult.cs). Это статическая проверка кода, а не результат испытаний.

## Границы

Входят валидация, наследование и копирование настроек, владение входными данными, смысл завершения отправки, классификация ошибок и сроков. Не входят очереди, сетевые повторы и реализация состояний транзакции; их проектируют шаги 03–05.

## Настройки и валидация

Согласовано сохранить `CommonConfig → ProducerConfig → TransactionalProducerConfig`. Производный тип задаёт `EnableIdempotence = true` и `Acks.All`; несовместимое изменение пользователем вызывает `KafkaConfigException` до сетевых действий. Исправлять параметры молча запрещено.

`ProducerConfig.EnableDeliveryReports` удаляется без замены. У продюсера нет режима, в котором уже принятая отправка остаётся без окончательного исхода. Существующий метод отправки с обработчиком доставки всегда передаёт итоговый результат без отдельного флага включения отчётов. Изменение его публичной сигнатуры не входит в этот шаг.

| Группа | Требуемая проверка |
|---|---|
| Размеры | Допустимые значения `BatchSize`, `BufferMemory`, `MaxRequestSize`, учёт заголовков и переполнения арифметики |
| Время | Конечность и диапазон `LingerMs`, сроки запросов и доставки, задержки повторов; исключение NaN и бесконечности |
| Подтверждения | Допустимый `Acks`, совместимость с идемпотентностью и транзакциями |
| Транзакции | Непустой `TransactionalId`, положительный срок, отдельная обработка отказа брокера по его пределу срока |
| Вложенные настройки | Компрессия, выбор раздела, безопасность и настройки брокеров проходят свои валидаторы |
| Ограничение параллелизма | Различить общий предел соединения и предел неподтверждённых запросов идемпотентного продюсера |

Проверяется итоговая конфигурация после наследования и пользовательской функции настройки. Ошибка указывает имя параметра, значение и причину без раскрытия секретов. Одинаковые настройки через разные перегрузки дают одинаковый результат проверки.

### Согласованный приоритет настроек

- Настройки общих сетевых соединений определяет кластер; параметры отправки определяет конфигурация продюсера.
- `BaseFrom` явно создаёт исходную конфигурацию на основе базовой. Затем пользователь изменяет нужные параметры продюсера; при создании клиента используются полученные значения.
- Создание клиента не определяет факт явного задания свойства по сравнению со значением по умолчанию. Значение, совпадающее с исходным, также может быть намеренно задано пользователем.
- Наследование `CommonConfig → ProducerConfig → TransactionalProducerConfig` сохраняется. Перенос настроек через `BaseFrom` и `MergeFrom` должен соблюдать указанное разделение ответственности и учитывать все применимые свойства, включая новые.

Этот принцип согласован. Точная принадлежность параметров, одновременно затрагивающих клиентскую операцию и общий сетевой ресурс, уточняется в таблице настроек; из принципа не следует разрешение отдельному продюсеру перенастраивать общее соединение.

### Согласованная независимость конфигурации

При создании клиента сохраняется независимый снимок применимых настроек, включая вложенные изменяемые данные. Последующие изменения исходной конфигурации влияют только на создаваемые позже клиенты и не меняют работающий экземпляр. Одну исходную конфигурацию можно использовать для создания нескольких клиентов без общей изменяемой конфигурации между ними.

Поверхностного `with` недостаточно: вложенные изменяемые объекты также копируются. Копирование выполняется при создании клиента, а не при каждой отправке. Итоговый снимок проходит валидацию до сетевых действий. Конкретная реализация копирования должна сохранять согласованный приоритет настроек.

## Сроки операций

| Срок | Назначение |
|---|---|
| `EnqueueTimeoutMs` | Согласовано: срок ожидания принятия записи, включая получение метаданных, выбор раздела и ожидание свободной памяти |
| `DeliveryTimeoutMs` | Согласовано: срок доставки с момента принятия записи, включая очередь, накопление пакета, сетевые попытки и повторы |
| `MaxQueuedMessages` | Согласовано: максимальное число принятых, но ещё не получивших окончательного исхода сообщений |
| `MaxPendingProduceRequests` | Согласовано: максимальное число вызовов, ожидающих принятия сообщения |
| `RequestTimeoutMs` | Один сетевой запрос в пределах оставшегося срока операции |
| `TransactionTimeoutMs` | Срок транзакции на стороне протокола, а не сумма сроков отдельных отправок |
| Общий срок освобождения | Согласовано: `CommonConfig.ClientDisposeTimeoutMs`, тип `int`, по умолчанию 10 000 мс; допустимы только положительные значения |
| `CloseConnectionTimeoutMs` | Закрытие физического соединения, отдельно от освобождения клиента |

Согласовано разделить сроки в `ProducerConfig`: `EnqueueTimeoutMs` ограничивает ожидание принятия записи, а `DeliveryTimeoutMs` — доставку уже принятой записи. `TransactionalProducerConfig` наследует оба параметра. Ожидание принятия асинхронное и не должно блокировать поток.

Срок `EnqueueTimeoutMs` начинается при вызове отправки и заканчивается принятием записи либо отказом. Срок `DeliveryTimeoutMs` начинается при принятии; время предыдущей фазы из него не вычитается. Поэтому `DeliveryTimeoutMs` не является общим пределом времени всего вызова. Повторы доставки не начинают этот срок заново. Точная внутренняя граница принятия и её синхронизация с отменой определяются в шаге 03.

Истечение срока до принятия означает, что запись не принята для отправки. Истечение срока доставки после возможной передачи брокеру не доказывает отсутствие записи. Согласованы тип `int`, единица измерения — миллисекунды, и следующие значения по умолчанию:

```csharp
public int EnqueueTimeoutMs { get; set; } = 60_000;
public int DeliveryTimeoutMs { get; set; } = 120_000;
public int MaxQueuedMessages { get; set; } = 100_000;
public int MaxPendingProduceRequests { get; set; } = 1_000;
```

Оба срока и пределы числа сообщений должны быть строго больше нуля. Ноль и отрицательные значения отклоняются валидатором через `KafkaConfigException` до сетевых действий; специальное значение для бесконечного ожидания не поддерживается. Эти ограничения относятся к указанным срокам и пределам числа сообщений и не задают диапазоны остальных параметров конфигурации.

Согласованная форма общей опции:

```csharp
public int ClientDisposeTimeoutMs { get; set; } = 10_000;
```

Единица измерения — миллисекунды. Ноль, отрицательные значения и бесконечное ожидание не допускаются; валидатор отклоняет недопустимое значение. Опция применяется к обычному и транзакционному продюсерам, потребителю и административному клиенту. Она не меняет назначения `CloseConnectionTimeoutMs`. Подробная политика истечения срока и ошибок освобождения согласуется отдельно.

Согласовано требование валидатора:

```text
DeliveryTimeoutMs >= LingerMs + RequestTimeoutMs
```

Оно гарантирует, что после принятия записи срок доставки покрывает накопление пакета и хотя бы одну полную сетевую попытку. Несовместимое сочетание отклоняется через `KafkaConfigException`; `Producer` не увеличивает `DeliveryTimeoutMs` автоматически. При повторе используется оставшееся время доставки, новый полный срок не начинается. `EnqueueTimeoutMs` не входит в это соотношение, потому что ограничивает отдельную фазу до принятия записи. Отмена ожидания и завершение сетевой операции — разные события. Механизм освобождения определяется в шаге 03, транзакционные последствия — в шаге 05.

### Согласованная отмена отправки

Токен отмены действует до включения записи в закрытый пакет. До этой границы отмена удаляет запись из очереди и гарантирует отсутствие её отправки. Задача и обработчик доставки получают одинаковый обычный результат: `PersistenceStatus.NotPersisted` с `ProducerError(ErrorCodes.ClientError, ProducerLocalError.Cancelled)`. Если отмена произошла до принятия, возвращается тот же результат без принятия записи; задача не переходит в состояние отмены.

После закрытия пакета токен отдельной записи не изменяет её судьбу: пакет не пересобирается, не разжимается и не прерывается из-за отмены одной записи. Это сохраняет целостность общего пакета, его порядок, сжатие, контрольную сумму и последовательности. Задача такой записи завершается окончательным `MessageDeliveryResult`; результат относится к фактическому исходу доставки.

Пользовательская отмена не отменяет уже записанные в соединение байты и не отменяет операцию на брокере. Остановка продюсера регулируется `DisposeAsync` и `ClientDisposeTimeoutMs`, а не токенами отдельных отправок.

## Владение сообщениями

### Согласованный договор владения сообщением

Продюсер не копирует ключ, значение и заголовки при принятии сообщения. С момента вызова `ProduceAsync` или отправки с обработчиком и до окончательного результата приложение не изменяет переданный `Message`, содержимое его массивов и состав `Headers`, а также не возвращает эти массивы в пул. Это договор использования публичного API, а не отдельная техническая блокировка объекта и не расширение контракта новыми буферными типами.

Окончательным результатом считается завершение возвращённой задачи либо вызов обработчика доставки. При отмене до закрытия пакета продюсер возвращает обычный результат `NotPersisted` с причиной `Cancelled`; после такого результата сообщение больше не используется продюсером. Правила отмены после закрытия пакета приведены в разделе сроков операций.

`Message` не получает новые флаги, блокирующие сеттеры, и не меняет форму публичного конструктора ради этого правила. Существующие возможности изменения состава `Headers` должны быть исключены из сценария отправляемого сообщения на время его использования продюсером. Рефлексия и намеренное изменение массивов после передачи не рассматриваются как поддерживаемый сценарий.

### Согласованный состав результата

`MessageDeliveryResult` сохраняет ссылку на исходный `Message`. Это позволяет вызывающему коду сопоставить итог отправки с данными сообщения без собственного словаря или замыкания. Результат также содержит статус, тему-раздел, смещение, временную метку и размеры сериализованных ключа и значения.

Библиотека удерживает результат и исходное сообщение только до завершения возвращённой задачи либо вызова обработчика доставки. Дальнейшее время жизни определяет вызывающий код: сохранённый результат удерживает и связанные массивы сообщения. Это следствие публичного состава результата, а не скрытый накопитель завершённых отправок внутри продюсера.

Временная метка результата — время записи, возвращённое Kafka при подтверждённой отправке. Для темы с `CreateTime` это временная метка исходного сообщения, для `LogAppendTime` — время добавления записи брокером. Если подтверждённого времени нет, в том числе при `Acks = 0`, `NotPersisted` и `PossiblyPersisted`, используется существующее значение `Timestamp.Default` с типом `NotAvailable`. Исходная метка времени остаётся доступной через `result.Message.Timestamp`.

### Согласованная семантика отсутствующих и пустых данных

Публичные свойства `Message.Key` и `Message.Value` становятся nullable:

```csharp
public byte[]? Key { get; set; }
public byte[]? Value { get; set; }
```

`null` и `Array.Empty<byte>()` имеют разный смысл и сохраняются без преобразования. `Value = null` формирует tombstone для compacted topic; пустой массив — обычную запись с пустым значением. `Key = null` и пустой ключ также различаются на уровне Kafka и могут по-разному влиять на выбор раздела. Никакая перегрузка, сериализация или копирование конфигурации не заменяет одно представление другим.

Значение заголовка также nullable:

```csharp
public void Add(string key, byte[]? value);
public sealed record Header(string Key, byte[]? Value);
```

`null` значение заголовка и пустой массив сохраняются как разные значения протокола. `Headers` остаётся изменяемым публичным типом: на текущем этапе не вводятся техническая блокировка, новый способ создания или копирование состава. При отправке действует согласованный договор не изменять состав `Headers` до окончательного результата. Договор отсутствия копирования распространяется и на nullable данные: после передачи нельзя заменять ссылки либо изменять или возвращать в пул непустые массивы до окончательного результата. Заголовки и выбор раздела должны одинаково трактоваться в обычной и транзакционной отправке.

## Результаты и ошибки

| Ситуация | Что вправе утверждать библиотека |
|---|---|
| Отказ до начала записи пакета в соединение | Запись не сохранена |
| Положительный ответ на Produce | Запись подтверждена согласно `Acks`; внутри транзакции это ещё не её подтверждение |
| `Acks = 0` | См. согласованную семантику ниже |
| Потеря ответа после возможной записи | Исход неизвестен; таймаут сам по себе не означает `NotPersisted` |
| Отмена пользовательского ожидания после принятия | Запись могла продолжить отправку; автоматический повтор приложением может создать дубликат |

### Согласованная семантика `Acks = 0`

Для `Acks = 0` окончательный локальный исход успешной передачи в сетевой путь представляется `PersistenceStatus.PossiblyPersisted`. Он означает, что клиент не получил от Kafka подтверждения сохранения: запись могла быть сохранена, а повтор со стороны приложения может создать дубликат.

В таком результате `Offset` равен `Offset.Unset`; подтверждённое брокером время отсутствует. Возвращаемая задача либо обработчик доставки завершаются после успешной передачи пакета в сетевой путь без ожидания ответа Produce. Разрыв соединения во время записи кадра также не доказывает отсутствие записи и не меняет этот статус на `NotPersisted`.

### Согласованная граница доказанного отказа

`PersistenceStatus.NotPersisted` используется только до начала записи содержащего сообщение пакета в соединение. В этой фазе библиотека доказывает, что Kafka не могла получить запись: сюда относятся отмена до закрытия пакета, истечение `EnqueueTimeoutMs` и ошибки локальной подготовки или очереди до начала записи.

После начала записи пакета отсутствие подтверждения Kafka всегда означает `PersistenceStatus.PossiblyPersisted`. Разрыв соединения, потеря ответа и истечение `DeliveryTimeoutMs` не доказывают отсутствие записи: брокер мог получить пакет, записать его или ожидать подтверждений реплик. Повтор такого сообщения может создать дубликат.

Ошибки аргументов и конфигурации возникают до принятия сообщения и передаются исключением вызова, а не результатом доставки. Точная классификация всех локальных причин реализуется в шаге 03.

### Согласованное представление исходов доставки

Задача и обработчик доставки сообщают один и тот же окончательный `MessageDeliveryResult`. Для любого штатного исхода уже принятой отправки задача завершается результатом, а не исключением: это исключает поток исключений при недоступности Kafka, переполнении очереди или массовых ошибках доставки.

`MessageDeliveryResult` дополняется свойством `ProducerError? Error`. Оно равно `null` только при подтверждённой доставке. Для ответа брокера `ProducerError` передаёт существующий `ErrorCodes` напрямую; новое перечисление, дублирующее ошибки протокола Kafka, не вводится. Локальная причина требуется только там, где у протокола нет соответствующего кода. Текст — только пояснение для диагностики; прикладной код не разбирает текст исключения.

Согласована форма ошибки:

```csharp
public sealed record ProducerError(
    ErrorCodes ErrorCode,
    ProducerLocalError LocalError);
```

В `ErrorCodes` добавляется `ClientError = short.MinValue`. `-1` для этой цели не используется, поскольку это уже протокольный `UnknownServerError`, который брокер вправе вернуть. Правила заполнения:

- `ErrorCode != ErrorCodes.ClientError` — ошибка пришла от Kafka; `LocalError = ProducerLocalError.None`.
- `ErrorCode == ErrorCodes.ClientError` — причина локальная и задаётся `LocalError`.
- `ErrorCode = ErrorCodes.None` недопустим для объекта ошибки.

`ProducerLocalError` начинается со значения `None = 0`, чтобы значение по умолчанию не обозначало ошибку. Публичная строка с описанием ошибки не хранится в `ProducerError`: для ошибок Kafka причина определяется `ErrorCodes`, для локальных — `ProducerLocalError`. Библиотека формирует текст только для журналов и диагностики. Для текущего этапа согласован следующий минимальный набор:

```csharp
public enum ProducerLocalError
{
    None = 0,
    Cancelled,
    RecordTooLarge,
    EnqueueTimedOut,
    DeliveryTimedOut,
    TransportFailure,
    ProducerClosing
}
```

Переполнение очереди не выделяется отдельно: при выбранной модели продюсер ждёт принятия сообщения до `EnqueueTimeoutMs`, затем возвращает `EnqueueTimedOut`. `RecordTooLarge` означает, что размер записи вместе с заголовками и служебными полями заведомо превышает установленный предел до её принятия продюсером. Новые локальные причины добавляются только при появлении сценария, который нельзя выразить существующими `ErrorCodes` или этим набором.

| Исход принятой отправки | `Status` | `Error` |
|---|---|---|
| Kafka подтвердила запись | `Persisted` | `null` |
| Запись могла сохраниться, но подтверждения нет | `PossiblyPersisted` | Причина неизвестного исхода |
| Отсутствие записи доказано | `NotPersisted` | Причина отказа |

Исключения остаются для ошибок вызова, которые невозможно выразить результатом: неверных аргументов, несовместимой конфигурации, обращения к освобождённому продюсеру и нарушения состояния транзакции. Исключение обработчика не меняет исход записи и не останавливает отправитель. Окончательное завершение каждой принятой записи происходит ровно один раз.

Таблица кодов Kafka, локальных причин и разрешённого продолжения разрабатывается совместно с шагами 04–05. Она учитывает фазу операции: один код Kafka сам по себе не всегда определяет, можно ли продолжать транзакцию или использовать продюсер.

## Граничные случаи и проверки

- Прямое создание, явный ID, готовая конфигурация и функция настройки проходят одинаковую проверку. Конфликт ID не изменяет входной объект и не резервирует идентификатор.
- Мутация вложенной конфигурации после создания не меняет работающий клиент. Проверяется перенос каждого свойства через `BaseFrom` и `MergeFrom`.
- Нулевые, отрицательные и предельные размеры, переполнение сумм, бесконечное время, неверная компрессия отвергаются предсказуемо.
- Потеря ответа не выдаётся за гарантированное отсутствие записи; задача и обработчик доставки согласованы.
- Ошибка очистки не должна незаметно уничтожать исходную ошибку приложения. Способ представления обеих ошибок обсуждается до реализации.

## Вопросы следующих шагов

Механизм очередей, выполнение обработчиков доставки, повторные попытки, сетевые состояния и освобождение клиента относятся к шагу 03. Идемпотентность, транзакционные ошибки и допустимость продолжения работы относятся к шагам 04–05. Изменение публичной сигнатуры существующего обработчика доставки и добавление обработчика транзакционному объекту требуют отдельного изменения публичного контракта; этот шаг их не определяет.

## Условия завершения

Согласованы значения, проверки и семантика, нужные для реализации настроек, данных, результатов и ошибок. Реализация должна сопровождаться модульными тестами и XML-документацией; руководства обновляются одновременно в `docs/en` и `docs/ru`. Наличие типов не считается подтверждением надёжности отправки.
