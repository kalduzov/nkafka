# План реализации шага 03.1 KIP-98

Цель: реализовать накопление, сериализацию и подготовку пакетов записей продюсера согласно [03.1-record-batch-accumulation.md](03.1-record-batch-accumulation.md), сохранив явный код без посредников и не изменяя сгенерированные файлы.

Работа выполняется последовательно. После каждого шага выполняются только относящиеся к нему проверки, затем работа останавливается для проверки пользователем. Коммиты не создаются без отдельного указания пользователя.

## Шаг 1. Явная модель состояний пакета

- Зафиксировать состояния `ProducerBatch`: открытый, закрытый, сжатый, окончательно сформированный, переданный отправителю и завершённый.
- Запретить добавление записей после закрытия, повторное закрытие и повторную сериализацию.
- Отделить готовность пакета к извлечению от факта его закрытия и отправки.
- Сохранить текущую модель завершения задач записей и обеспечить корректное завершение пустого/служебного пакета.
- Добавить модульные проверки допустимых переходов и запрета операций в конечных состояниях.
- Проверить затронутый проект и тесты пакета.

Результат: пакет имеет проверяемый жизненный цикл, но расчёт лимитов, двоичная сериализация и отправка ещё не считаются завершёнными.

## Шаг 2. Расчёт верхней границы и учёт памяти

- Определить единый расчёт безопасной верхней границы записи с учётом ключа, значения, заголовков, длин и служебных полей.
- Разделить размер записи, размер закрытого пакета и размер Produce-запроса.
- Проверять `MaxRequestSize` до выделения буфера и возвращать результат `NotPersisted` с `ClientError/RecordTooLarge` для слишком большой записи.
- Учесть отдельный пакет для записи больше `BatchSize`, не позволяя ему обходить локальный и протокольный лимиты.
- Проверить переполнение целочисленных расчётов и возврат буферов во всех ветках.
- Добавить модульные проверки границ и отсутствия лишнего резервирования.

Результат: до принятия записи известна безопасная граница, а буфер выделяется только для допустимой записи.

## Шаг 3. Формирование двоичного RecordBatch

- Восстановить запись тела `Record` в накопленный буфер в порядке принятия.
- Сформировать заголовок `RecordBatch`: длину, число записей, смещения, временные метки, атрибуты, значения отсутствия идемпотентности и резервируемые поля шага 04.
- Рассчитать относительные смещения и дельты временных меток относительно первой записи.
- Рассчитать CRC по протокольному диапазону и записать его в заголовок.
- Сделать итоговые байты неизменяемыми и исключить повторную сериализацию.
- Проверить байты независимым чтением через `RecordBatch`, CRC, порядок, null-значения и заголовки.

Результат: закрытый пакет можно передать в Produce-запрос как корректный Kafka `RecordBatch`.

## Шаг 4. Сжатие закрытого пакета

- Выполнять сжатие ровно один раз после закрытия всего пакета.
- Резервировать временную память с учётом `BufferMemory` и освобождать её после завершения операции.
- Устанавливать протокольные атрибуты сжатия и пересчитывать длину и CRC после сжатия.
- При локальной ошибке сжатия один раз продолжать с тем же пакетом без сжатия.
- Не считать сжатие способом обхода `MaxRequestSize` и проверять итоговый размер.
- Добавить проверки для всех поддерживаемых типов сжатия и отказа с возвратом к несжатому варианту.

Результат: пакет содержит неизменяемое сжатое или явно несжатое представление, пригодное для повторной отправки.

## Шаг 5. Извлечение пакетов и порядок раздела

- Исправить извлечение строго первого готового пакета из очереди раздела.
- Проверять готовность именно у первого пакета; `LingerMs` отсчитывать от первого сообщения.
- Объединять первые готовые пакеты разных разделов одного брокера до `MaxRequestSize` с учётом служебных полей запроса.
- Ограничить Produce-запрос одним пакетом на раздел и не создавать меньшие пакеты при переполнении запроса.
- Для одиночного пакета, превышающего лимит запроса, завершать его записи как `NotPersisted/RecordTooLarge`.
- Добавить проверки порядка, границ запроса и поведения при пустых/не готовых очередях.

Результат: отправитель получает пакеты в правильном порядке и с точным ограничением размера запроса.

## Шаг 6. Границы FlushAsync и завершение результатов

- Ввести кратковременный барьер принятия сообщений для каждого вызова `FlushAsync`.
- Атомарно зафиксировать записи, вошедшие в границу вызова, закрыть их пакеты без ожидания `LingerMs` и сохранить задачи завершения.
- Снять барьер до ожидания, чтобы более поздние записи не попали в текущую границу.
- Обеспечить независимые границы одновременных вызовов и ожидание только своей группы задач.
- При отмене отменять только ожидание вызывающего кода, не уже принятые записи.
- Проверить завершение после смешанных успехов и ошибок без агрегирования ошибок в `FlushAsync`.

Результат: `FlushAsync` имеет семантику Java Kafka и не теряет границу между параллельными вызовами.

## Шаг 7. Сквозная проверка и интеграция отправки

- Согласовать подготовленный пакет с `MessagesSender` и формированием Produce-запроса.
- Проверить ответы `MessageTooLarge` и `RecordListTooLarge` с завершением затронутых записей кодом брокера.
- Добавить межклиентскую/брокерную проверку чтения каждого поддерживаемого сжатого пакета, если доступен брокер.
- Запустить целевые модульные тесты для .NET 8 и .NET 9, отдельно зафиксировать ограничения среды и результаты интеграционных тестов.
- Сверить каждый пункт исходной спеки и обновить статус реализации.

Результат: все требования шага 03.1 подтверждены кодом и проверками либо явно отмечены как недоступные для проверки в текущей среде.
