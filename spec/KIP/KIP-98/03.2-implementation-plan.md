# План реализации шага 03.2 KIP-98

Цель: завершить надёжную отправку обычного и транзакционного продюсеров по согласованной спецификации [03.2](03.2-reliable-delivery-and-resources.md), сохраняя ограничение памяти, порядок записей и единственный окончательный результат для каждой принятой записи.

Уже выполнено отдельными проверенными изменениями: повтор временных ошибок, предел ожидающих вызовов и принятых записей, учёт `BufferMemory`, пробуждение отправителя без задержки после успеха, завершение ожидающих операций при закрытии, запись запросов без ответа для `Acks.None`, последовательная защита общей записи кадра и классификация исхода неудачной записи `Acks.None`.

Параллельная отправка на разные узлы и общая политика распределения соединений не входят в этот план: они отнесены к отдельному предложению 03.3 и требуют отдельного согласования. Здесь запросы к узлам остаются последовательными.

## Шаг 1. Объединение разделов одного узла в Produce-запрос — следующий

- Сгруппировать готовые пакеты по узлу-лидеру и сформировать один Produce-запрос на узел за проход отправителя.
- В запросе объединить разделы одного топика, сохраняя не более одного пакета на раздел и порядок пакетов.
- Сопоставить каждый ответ раздела с исходным пакетом; отдельно обработать успех, постоянную ошибку, временную ошибку, отсутствующий или повторный ответ.
- При ошибке всего запроса завершить или повторно поставить на отправку все его пакеты согласно `Acks` и общему сроку доставки.
- Для `Acks.None` завершить все пакеты только после успешной записи запроса; при ошибке записи не повторять их.
- Добавить проверки: один запрос для нескольких разделов одного узла, два запроса для разных узлов, смешанные ответы, неполный ответ и ошибка общего запроса.

Результат: уменьшается число сетевых запросов без изменения согласованной последовательности отправки между узлами.

## Шаг 2. Ожидание уже отправленных пакетов во время FlushAsync

- Сохранять отслеживание каждого принятого пакета после извлечения из очереди и до окончательного завершения.
- Включать в ожидание `FlushAsync` пакеты в очереди, на отправке и в повторе.
- Сохранить отмену только ожидания вызывающего кода, не отменяя принятые записи.
- Проверить повторный вызов, параллельную отправку, повтор и отмену ожидания.

Результат: `FlushAsync` не возвращается, пока не завершены затронутые им пакеты.

## Шаг 3. Ограниченный срок освобождения продюсера

- Применить `ClientDisposeTimeoutMs` к единой операции асинхронного освобождения.
- Не освобождать буфер и ресурсы отправителя, пока к ним может обращаться незавершённая отправка.
- Различать пакеты, передача которых не начиналась, и пакеты с неопределённым исходом.
- Сделать повторный `DisposeAsync` присоединённым к тому же завершению.
- Добавить проверки обычного завершения, зависшей отправки, истечения срока и повторного вызова.

Результат: освобождение ограничено согласованным сроком и не создаёт гонок с сетевой отправкой.

## Шаг 4. Сверка повторов и владения результатами

- Проверить все временные коды Produce и обновление метаданных только для ошибок лидера.
- Проверить общий срок доставки, учёт повторов и освобождение пакетов при всех ответах и исключениях.
- Убедиться, что ни один принятый результат не остаётся незавершённым.
- Не менять правила идемпотентных последовательностей шага 04.1.

Результат: повторы не теряют пакеты и не продлевают срок доставки.

## Шаг 5. Проверка шага и фиксация ограничений среды

- Запустить целевые модульные проверки и сборки для доступных версий .NET.
- Проверить поведение общих соединений на административных запросах и запросах потребителя.
- Выполнить доступные проверки с брокером и отдельно отметить недоступные среды.
- Сверить условия завершения спецификации 03.2 и обновить этот план.

Результат: каждое условие имеет подтверждающую проверку либо явно записанное ограничение.

## Правило остановки

После завершения каждого шага работа останавливается для проверки пользователем. Изменения отдельного шага фиксируются только после его явного одобрения.
