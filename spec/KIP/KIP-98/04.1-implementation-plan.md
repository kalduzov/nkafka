# План реализации шага 04.1 KIP-98: базовая идемпотентность

Цель: для обычного продюсера включить защиту Kafka от дубликатов при внутреннем повторе Produce-запроса, сохранив согласованный порядок записей и работу независимых разделов.

## Этап 1. Получение ProducerId и проверка возможностей протокола

- Запускать получение ProducerId фоновым отправителем для обычного продюсера; синхронный `CreateProducer` не должен выполнять сетевых запросов.
- Обеспечить, чтобы принятые сообщения ожидали `InitProducerId`, а идемпотентный Produce не отправлялся до его успешного завершения.
- Проверять наличие `InitProducerId` и поддерживаемой версии Produce с полями идемпотентности по согласованным возможностям брокера либо резервной матрице.
- Передавать в `InitProducerId` пустой `TransactionalId`; при `EnableIdempotence = false` не вызывать этот запрос.
- Повторять временные ошибки в пределах `DeliveryTimeoutMs`; после окончательного отказа завершать ожидающие и последующие отправки с `NotPersisted`, `ClientError` и `ProducerLocalError.IdempotenceInitializationFailed`.
- Проверить успешный ответ, временные и окончательные ошибки брокера, отсутствие API, отмену и неисправное состояние; добавить модульные проверки.

## Этап 2. Метаданные последовательности в RecordBatch

- Передавать в сериализацию `ProducerId`, эпоху и начальную последовательность.
- Сохранять прежние значения для пакетов без идемпотентности и проверять точные байты заголовка.
- Проверить границы значений и повторную сериализацию неизменяемого пакета.

## Этап 3. Последовательности по разделам и единственный пакет в полёте

- Вести состояние последовательности отдельно для каждого `TopicPartition`.
- Выдавать диапазон по числу записей один раз при создании логического пакета.
- Не отправлять следующий пакет раздела до окончательного исхода предыдущего; не задерживать независимые разделы.
- Добавить проверки независимости разделов и разных экземпляров продюсера на общем соединении.

## Этап 4. Повтор того же пакета и защита от дубликатов

- При внутреннем повторе сохранять ProducerId, эпоху, начальную последовательность и итоговые байты.
- Проверить потерю ответа, повтор и единственную запись при чтении из Kafka.
- Проверить, что отдельный вызов приложения остаётся отдельной записью.

## Этап 5. Итоговые проверки и документация

- Запустить относящиеся к продюсеру тесты и сборки для поддерживаемых целевых платформ.
- Выполнить доступные испытания с брокером; явно отметить недоступные проверки.
- Описать ограничения обычного идемпотентного продюсера в XML и руководствах `docs/en` и `docs/ru`.

## Правило фиксации

Каждый этап реализуется отдельным узким изменением, сопровождается относящимися к нему тестами и проверками. Перед каждым коммитом работа останавливается для проверки пользователем; в коммит включаются только перечисленные файлы текущего этапа.
