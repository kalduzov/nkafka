# Шаг 05. Протокол, состояния и время жизни транзакционного продюсера

Статус: согласовано, готово к реализации. Протокольная реализация транзакций ещё не завершена. Согласованные ограничения из [шага 01](01-public-interfaces.md) сохраняются.

## Цель и зависимости

Зависимость: шаги 02–04.2. Объект транзакции действительно объединяет записи в нескольких темах и разделах, подтверждает или отменяет их на брокере и безопасно переживает ошибки. Публичные методы больше не ограничиваются переходом локального состояния или возвратом завершённой задачи. Этот шаг реализует классический путь KIP-98; новый серверный режим Kafka 4.x намеренно отложен до завершения шага 07.

## Текущее состояние

[TransactionalProducer](../../../src/NKafka/Clients/Producer/TransactionalProducer.cs) и [ProducerTransaction](../../../src/NKafka/Clients/Producer/ProducerTransaction.cs) делегируют операции внутреннему продюсеру. Объект транзакции пока не проверяет собственную завершённость, его `DisposeAsync` ничего не делает. В [TransactionManager](../../../src/NKafka/Clients/Producer/Internals/TransactionManager.cs) обработка ответа инициализации не завершена, поиск координатора пуст, подтверждение и отмена не выполняют необходимый протокол. В [KafkaCluster](../../../src/NKafka/KafkaCluster.cs) ID резервируется до конструктора `Producer`, но конструктор находится вне блока очистки при ошибке; отказ очистки также требует отдельной обработки.

## Границы и согласованные ограничения

Отправка возможна только через `IProducerTransaction`; один продюсер имеет одну незавершённую транзакцию. Новый вызов создания возвращает новый экземпляр после сетевой инициализации. Реестра повторного использования нет. Занятый ID запрещён в пределах одного `IKafkaCluster`, включая инициализацию и освобождение. Объект кластера владеет общими соединениями; отдельный сокет транзакционному продюсеру по умолчанию не требуется.

Включение смещений потребителя выделено в шаг 06. До его завершения `SendOffsetsAsync` не должен ложно сообщать успех: временное ограничение должно быть явным. Обёртки автоматического выполнения и повтора пользовательской функции не входят в этот шаг.

## Создание и занятость ID

1. Сформировать независимую итоговую конфигурацию и выполнить валидацию до сетевых действий.
2. Атомарно занять ID; второй вызов не инициализирует ещё одного продюсера и не влияет на первого.
3. Найти координатора транзакций и самостоятельно повторять временные ошибки и смену координатора. На текущем этапе общий срок создания задаёт только `CancellationToken` вызывающего кода; новая настройка срока не вводится.
4. Возвратить готовый экземпляр без открытой транзакции только после получения корректного состояния.
5. При окончательном отказе, включая конструктор и очистку, завершить собственные операции и затем освободить ID. Сохранить первопричину ошибки. Метод бросает исключение и не возвращает частично инициализированный экземпляр; пользователю нечего отменять или освобождать. Отмена ожидания не освобождает ID мгновенно: она сначала останавливает или очищает внутреннюю инициализацию, после чего ID освобождается безопасно.

В целевой модели ни одна операция библиотеки не ожидает бесконечно: для каждой будет определён конечный срок из настроек либо явно переданного срока. Пользователь, установивший чрезмерно большой срок, сам принимает это следствие. Общий механизм сроков и повторов, не относящийся только к транзакциям, проектируется отдельной спецификацией.

При закрытии кластера одновременно с созданием нельзя вернуть работоспособный на вид клиент поверх закрытых ресурсов. Локальный учёт не защищает от экземпляра с тем же ID в другом процессе: вытеснение на брокере должно окончательно запрещать операции старого экземпляра.

Согласовано для транзакционного продюсера в целом: минимальная поддерживаемая версия кластера Kafka — 2.5. `CreateTransactionalProducerAsync` не возвращает экземпляр, если кластер не удовлетворяет этому требованию; отказ проходит через обычную очистку создания и освобождение занятого `TransactionalId`. Это ограничение действует и для транзакций без смещений потребителя. Обычный продюсер сохраняет свою минимальную поддерживаемую версию Kafka 2.0. Конкретный способ проверки версии и возможностей каждого необходимого брокера определяется при реализации; нельзя полагаться на версию только одного узла смешанного кластера.

## Состояния и объект транзакции

Таблица описывает смысл внутренних состояний; она не требует добавлять публичное перечисление.

| Состояние | Допустимые операции |
|---|---|
| Готов | Начать новую транзакцию, освободить продюсер |
| Транзакция активна | Принять запись или смещения, начать подтверждение или отмену |
| Требуется отмена | Отмена либо освобождение с допустимой попыткой отмены |
| Подтверждение выполняется или его исход неизвестен | Продолжить то же решение либо освободить продюсер; новые записи запрещены |
| Отмена выполняется или её исход неизвестен | Продолжить отмену либо освободить продюсер |
| Транзакция завершена | Немедленно начать следующую транзакцию либо освободить прежний объект |
| Продюсер вытеснен, неисправен или освобождается | Новые операции запрещены; завершаются ожидающие и ресурсы |

Каждый объект транзакции привязан к своему поколению, чтобы старая ссылка не могла отправить запись в следующую транзакцию того же продюсера. Начало завершения атомарно закрывает приём. Параллельные отправки одной активной транзакции допустимы в пределах правил шага 03.2. Независимые управляющие вызовы должны иметь определённый порядок или понятный отказ, а не случайное переключение общего состояния.

Пока у продюсера есть активная транзакция, второй и последующие вызовы `BeginTransactionAsync` запрещены и завершаются исключением нарушения состояния. Метод не возвращает существующий объект: без отдельного ключа идемпотентности нельзя отличить повтор вызова от независимой прикладной операции, а неявное объединение обеих операций в одну транзакцию небезопасно.

`BeginTransactionAsync` атомарно создаёт только локальный объект транзакции и не выполняет ввод-вывод. Его токен отмены проверяется до смены состояния. Первая сетевая операция возникает при `ProduceAsync` или `SendOffsetsAsync`. `CommitAsync` и `AbortAsync` действительно пустой транзакции, в которой не принята ни запись, ни смещения, завершаются локально без обращения к координатору. Если принята хотя бы одна запись, применяется обычный протокол независимо от того, успел ли её пакет уйти в сеть.

`TransactionTimeoutMs` для протокольных повторов начинается с первой отправки `AddPartitionsToTxn` либо операции со смещениями, то есть когда координатор впервые узнаёт о транзакции. Пустой объект транзакции без записей и смещений не создаёт состояния на брокере и не истекает сам по себе; его `DisposeAsync` завершает работу локально.

При принятии первой записи для раздела `Producer.InternalProduceAsync` вызывает `TransactionManager.TryAddPartition`, который только атомарно помечает раздел ожидающим включения и будит `MessagesSender`. `RecordAccumulator` не выполняет сетевых операций. В начале следующего цикла `MessagesSender.RunOnceAsync` вызывает новый метод `TransactionManager.AddPendingPartitionsAsync`: он находит координатора, формирует `AddPartitionsToTxnRequestMessage`, вызывает `KafkaCluster.SendAsync` и переносит подтверждённые разделы в набор включённых. Затем `MessagesSender.SendProducerDataAsync` отправляет Produce только для включённых разделов. Пакет раздела, появившийся после снимка ожидающих включений, возвращается в накопитель и ждёт следующего вызова `AddPendingPartitionsAsync`; это устраняет гонку между параллельным `ProduceAsync` и отправителем.

`AddPartitionsToTxn` обрабатывается по разделам ответа. Успешный раздел становится включённым и его Produce разрешается независимо от результата соседних разделов. Временные отказы, смена координатора и `ConcurrentTransactions` оставляют раздел ожидающим и повторяются в пределах оставшегося срока транзакции. Неисправимая ошибка включения переводит всю транзакцию в `RequiresAbort`, не отправляя ещё не включённые разделы. Вытеснение, отказ в правах на `TransactionalId` и неподдержанный протокол переводят экземпляр в `IsFatal`. Отказ в правах на отдельную тему (`TOPIC_AUTHORIZATION_FAILED`) переводит текущую транзакцию в `RequiresAbort`, но не запрещает использовать продюсер после подтверждённой отмены. Это повторяет внешнюю семантику librdkafka: управляющие запросы повторяются автоматически до успеха или окончания срока транзакции; затем ошибка становится отменяемой либо фатальной.

`OPERATION_NOT_ATTEMPTED` означает, что соответствующий раздел не включён в транзакцию из-за ошибки другого раздела в том же ответе. Решение принимается по всему ответу: временная причина ведёт к повтору невключённых разделов, ошибка с `RequiresAbort` или `IsFatal` определяет состояние всей транзакции. Если в ответе нет иной причины, включение повторяется до окончания срока транзакции; затем возвращается `RequiresAbort`. Ни один раздел с `OPERATION_NOT_ATTEMPTED` не допускается к `Produce` до подтверждения включения.

После подтверждённого завершения транзакции продюсер может начать следующую, не ожидая `DisposeAsync` прежнего объекта. Старый объект сохраняет только результат выбранного завершения; отправка, добавление смещений и противоположное решение запрещены проверкой поколения. Это сохраняет семантику Java-клиента Kafka и librdkafka, где следующая транзакция начинается сразу после завершения предыдущей.

Первый вызов `CommitAsync` или `AbortAsync` атомарно выбирает решение и запускает одну внутреннюю операцию завершения, которая не зависит от времени жизни ожидания отдельного вызывающего кода. Повтор того же вызова присоединяется к её результату; его токен отменяет только ожидание этого вызывающего кода. Противоположный вызов получает исключение нарушения состояния. После подтверждённого завершения повтор того же вызова возвращает сохранённый успешный результат без нового запроса. После освобождения объекта новые вызовы запрещены.

`CommitAsync` сначала закрывает приём и ожидает завершения всех ранее принятых отправок. Если хотя бы одна из них завершилась с `NotPersisted` или `PossiblyPersisted`, подтверждение `EndTxn(commit)` не посылается. Вызов возвращает ошибку, а транзакция переходит в состояние «требуется отмена»; отмену явно начинает вызывающий код. Это соответствует поведению Java-клиента Kafka и librdkafka.

При временной сетевой ошибке или истечении срока ожидания ответа `EndTxn(commit)` решение не меняется: тот же запрос с теми же идентификатором, эпохой и решением повторяется в пределах оставшегося срока транзакции. При смене координатора обновляется маршрут. Повторный `CommitAsync` присоединяется к внутренней операции. `AbortAsync` запрещён, поскольку фиксация уже могла начаться. Если исход не удаётся установить до окончания срока транзакции, выбрасывается фатальная ошибка и экземпляр не начинает следующую транзакцию.

При временной сетевой ошибке или истечении срока ожидания ответа `EndTxn(abort)` тот же запрос с теми же идентификатором, эпохой и решением повторяется в пределах оставшегося срока транзакции. При смене координатора обновляется маршрут. Повторный `AbortAsync` присоединяется к внутренней операции. `CommitAsync` запрещён, поскольку отмена уже могла начаться. Если исход не удаётся установить до окончания срока транзакции, выбрасывается фатальная ошибка и экземпляр не начинает следующую транзакцию.

`AbortAsync` сразу закрывает приём новых отправок, дожидается окончательных результатов всех ранее принятых отправок по правилам шага 02 и затем выполняет `EndTxn(abort)`. Отмена не переписывает результаты отправок задним числом: `Persisted` означает подтверждение Produce, но после успешной отмены запись не выдаётся читателю с `read_committed`.

## Ошибки транзакции для вызывающего кода

Все исключения Kafka получают в базовом `KafkaException` nullable-свойство кода ответа брокера:

```csharp
public ErrorCodes? ErrorCode { get; }
```

Оно заполняется только кодом, полученным от Kafka, и предназначено для журналов и диагностики; локальные ошибки имеют `null`. Существующее свойство `ProtocolKafkaException.InternalError` сохраняется как устаревший совместимый псевдоним `ErrorCode`.

Управляющие методы транзакции используют существующий публичный `TransactionException`. В нём добавляются два публичных признака:

```csharp
public bool RequiresAbort { get; }

public bool IsFatal { get; }
```

Признаки взаимоисключающие. `RequiresAbort` означает, что текущую транзакцию нельзя подтвердить: вызывающий код вызывает `AbortAsync`, а после его успешного завершения может начать новую транзакцию и повторить прикладную единицу работы. `IsFatal` означает, что экземпляр нельзя больше использовать; вызывающий код освобождает его и создаёт новый. `TransactionException` наследует `ErrorCode`, но вызывающий код не разбирает код протокола, чтобы принять это решение.

Временные сетевые отказы и смена координатора повторяются библиотекой в пределах оставшегося срока транзакции и не получают отдельного публичного признака. Отмена токена у `CommitAsync` или `AbortAsync` отменяет только ожидание вызывающего кода: он повторяет тот же метод, который присоединяется к уже выбранному решению. Если исход управляющей операции не установлен до окончания срока транзакции, выбрасывается `TransactionException` с `IsFatal = true`.

Ответ `TRANSACTION_ABORTABLE` на `EndTxn(commit)` переводит транзакцию в `RequiresAbort`: вызывающий код отменяет её. Тот же ответ на `EndTxn(abort)` переводит экземпляр в `IsFatal`: повтор отмены не может устранить ошибку, возникшую при самой отмене.

`UNKNOWN_PRODUCER_ID` допускает восстановление только при поддержке `InitProducerId` версии 3 или выше: текущая транзакция получает `RequiresAbort`, а после подтверждённой отмены и до следующей транзакции продюсер обновляет свою эпоху. Если координатор не поддерживает такое обновление, экземпляр получает `IsFatal`. Если `UNKNOWN_PRODUCER_ID` получен на `EndTxn(abort)`, экземпляр получает `IsFatal` независимо от поддержки обновления эпохи: повтор отмены не считается безопасным восстановлением.

`INVALID_TXN_STATE` и `INVALID_PRODUCER_ID_MAPPING` переводят транзакционный продюсер в `IsFatal` при добавлении раздела, отправке или завершении транзакции. Новая транзакция на этом экземпляре запрещена.

Неизвестный NKafka числовой код ошибки брокера на `AddPartitionsToTxn` переводит транзакцию в `RequiresAbort`; на `EndTxn` — экземпляр в `IsFatal`. Неизвестный код при сетевой инициализации завершает `CreateTransactionalProducerAsync` исключением без возвращения экземпляра. Числовое значение сохраняется в `KafkaException.ErrorCode` для диагностики, даже если ему пока не соответствует именованный элемент `ErrorCodes`.

## Последовательность протокола

| Фаза | Обязательство реализации |
|---|---|
| Инициализация | Маршрут к координатору, корректные `InitProducerId`, идентификатор и эпоха, разбор всех ответов |
| Первый вход раздела | Включить раздел в транзакцию запросом `AddPartitionsToTxn` до зависимой отправки `Produce` |
| Отправка | Передать транзакционный признак пакета, ID, эпоху, последовательность и необходимые поля Produce |
| Подтверждение | Закрыть приём, дождаться всех принятых операций, проверить накопленные ошибки, выполнить подтверждение `EndTxn` |
| Отмена | Остановить новые отправки, дождаться результатов ранее принятых отправок, затем выполнить отмену по протоколу |
| Смена координатора | Обновить маршрут и продолжить только допустимую операцию в оставшийся срок |

Версии запросов транзакционного продюсера выбираются в одной внутренней точке по пересечению возможностей конкретного брокера, поддерживаемых версий NKafka и пределов классического KIP-98. Обычный продюсер использует общий порядок согласования версий без транзакционных пределов. Выбранный режим сохраняется на время транзакции; внутри неё переход между протоколами запрещён. На этом шаге доступен только классический режим, без пользовательской настройки выбора. Отдельная иерархия стратегий для одного режима не требуется.

При `CreateTransactionalProducerAsync` проверяются общие версии `FindCoordinator` и `InitProducerId` у брокеров, участвующих в инициализации. Общая версия остальных запросов проверяется у конкретного брокера перед их отправкой, в том числе после смены координатора или ведущего раздела. Отсутствие общей версии завершается явной ошибкой соответствующей операции; уже принятая запись получает окончательный результат по правилам шага 02 и не остаётся ожидать в очереди. Проверка всех возможных ведущих брокеров при создании продюсера не требуется.

Для классического KIP-98 применяются следующие верхние пределы версий запросов: клиентский `AddPartitionsToTxn` — 3, транзакционный Produce — 11, `EndTxn` — 4, `InitProducerId` — 5. `EndTxn` 4 добавляет код ошибки `TRANSACTION_ABORTABLE`, но не обновляет эпоху по окончании каждой транзакции; это поведение начинается с версии 5. `InitProducerId` 5 также добавляет этот код ошибки; версия 6 вводит поля двухфазного протокола и не применяется в этом шаге. `FindCoordinator` не имеет отдельного транзакционного верхнего предела: выбирается новейшая общая версия не ниже 1, а ответы версий до 4 и начиная с 4 разбираются по соответствующим схемам. Проверяются [схемы сообщений](../../../resources/message/EndTxnRequest.json). Более новые версии запросов не выбираются только потому, что их объявил брокер. Режим Kafka 4.x с `transaction.version=2` не активируется в рамках этого шага и рассматривается отдельно в шаге 09.

Подтверждение учитывает ошибки всех принятых операций, даже если приложение не ожидало их задачи. Неудачная проверка аргумента до принятия не обязана портить транзакцию; ошибка принятой операции классифицируется по шагу 02. Ошибки авторизации, вытеснение, смена координатора и сетевой таймаут не сводятся к одной политике повтора.

## Неизвестный исход и освобождение

Успех Produce не равен успеху всей транзакции. Потеря ответа на завершение не даёт права автоматически повторить прикладную работу. Выбранное решение сохраняется; после неоднозначного ответа продолжается только оно, без переключения на противоположное. Правила сверяются с выбранным протоколом и [контрактом KafkaProducer](https://kafka.apache.org/38/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html).

Освобождение активной транзакции атомарно закрывает приём новых сообщений и пытается отменить её без автоматического подтверждения. Оно использует общий `ClientDisposeTimeoutMs`. При неизвестном исходе отмены подтверждение не посылается; если безопасное завершение не доказано, экземпляр не начинает новую транзакцию.

Явный `AbortAsync` возвращает ошибку отмены вызывающему коду. Автоматическая отмена при `IProducerTransaction.DisposeAsync` или освобождении транзакционного продюсера имеет другую цель: закрыть экземпляр, не подменив исключение из прикладного кода. Поэтому ошибки этой попытки и истечение её срока не выбрасываются из `DisposeAsync`: они записываются в журнал и учитываются отдельной метрикой исхода освобождения. Если приложению требуется подтверждение отмены от брокера, оно вызывает `AbortAsync` явно до освобождения. Успешное завершение `DisposeAsync` само по себе не доказывает отмену на брокере; это отражается в XML-документации и руководствах на обоих языках.

Используется единый срок освобождения из шага 02: вложенная очистка не получает новый полный срок. Повторное освобождение ждёт ту же операцию. Истечение срока завершает локальное ожидание без заявления об отмене на брокере. После завершения локального `DisposeAsync` ID освобождается и при неизвестном исходе отмены: старый экземпляр атомарно запрещает свои дальнейшие сетевые действия, а новый экземпляр с тем же ID проходит `InitProducerId`, который окончательно вытесняет старый на стороне Kafka. Ошибка очистки не оставляет вечную локальную блокировку.

## Требования к руководству по использованию

Перед выпуском функции в `docs/en` и `docs/ru` добавляются одинаковые по структуре сценарии бизнес-кода:

- длительно работающий обработчик сам создаёт и освобождает один транзакционный продюсер, не регистрируя его экземпляр в контейнере зависимостей;
- несколько параллельных прикладных операций отправляют записи через явно переданный один объект транзакции, после чего координатор подтверждает её;
- независимые потоки событий используют очередь единственного владельца либо отдельные продюсеры с разными `TransactionalId`;
- создание продюсера, временная недоступность координатора, отмена ожидания создания и окончательный отказ без возвращённого экземпляра;
- обработка `TransactionException.RequiresAbort`, `TransactionException.IsFatal` и отмены ожидания управляющего метода.

## Граничные случаи и проверки

- Транзакция нескольких разделов: подтверждённые записи доступны независимому читателю `read_committed`, отменённые не выдаются.
- Пустая транзакция, повторный `Begin`, старая ссылка после следующего `Begin`, операции после освобождения.
- Отправка одновременно с подтверждением: каждая запись либо принята в эту транзакцию, либо отвергнута; не попадает в следующую.
- Отмена с пакетами в очереди и выполняющимися попытками: все они завершаются по правилам шага 02; ранее подтверждённые записи не видны читателю `read_committed`.
- Ошибка принятой отправки при неожидаемой задаче не позволяет успешно подтвердить транзакцию.
- Потеря ответа до и после фиксации, смена координатора, отказ авторизации, истечение срока транзакции.
- Два процесса с одним ID: старый экземпляр получает окончательный отказ; локальная проверка не подменяет этот тест.
- Отказ конструктора после резервирования, ошибка и отмена инициализации, ошибка очистки, одновременное закрытие кластера.
- Обычные и несколько транзакционных продюсеров используют общие соединения без смешения состояния.

## Условия завершения

Нет успешных заглушек. Переходы проверены модульно, атомарность и вытеснение — на настоящем брокере с независимым читателем. Все ветви создания освобождают ресурсы и ID. XML и обе версии руководства содержат явное владение из кода и предупреждение об общем `singleton`. Готовность этого шага ещё не означает готовность обработки со смещениями.
