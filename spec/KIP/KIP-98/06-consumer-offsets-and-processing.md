# Шаг 06. Смещения потребителя и обработка сообщений в транзакции

Статус: черновик для отдельного обсуждения. Создание документа не означает согласования новых решений или реализации функциональности. Согласованные ограничения из [шага 01](01-public-interfaces.md) сохраняются. Ниже требования описывают целевое поведение; предложенные варианты и открытые вопросы принимаются отдельно перед реализацией.

## Цель и зависимости

Зависимость: шаг 05 и результаты шага 02. Атомарно подтверждать выходные записи и следующие позиции обработанных входных записей в одном Kafka-кластере. После сбоя приложение должно возобновлять работу с согласованного состояния группы.

## Текущее состояние

В [ProducerTransaction](../../../src/NKafka/Clients/Producer/ProducerTransaction.cs) метод смещений делегирует вызов внутреннему продюсеру; в [TransactionManager](../../../src/NKafka/Clients/Producer/Internals/TransactionManager.cs) он возвращает завершённую задачу без протокольных действий. Тип `ConsumerGroupMetadata` уже существует, но наличие типа не доказывает получение актуального согласованного состояния группы от потребителя. Требуется проверить публичный способ получения этих данных и поведение потребителя при чтении транзакционных записей.

## Границы

Входят `SendOffsetsAsync`, маршрутизация к координаторам, актуальные сведения о группе, минимальные необходимые изменения потребителя и законченный пример обработки. Не входят полная переработка потребителя, Kafka Streams, транзакции между кластерами и атомарная запись во внешнюю базу данных.

## Договор с потребителем

В метод передаются позиции следующих записей, а не последних обработанных. Для каждого раздела приложение передаёт позицию только после обработки всех записей перед ней; при параллельной обработке нельзя подтверждать позицию за незавершённой записью.

Согласовано: по аналогии с Java Kafka аргумент смещений в `SendOffsetsAsync` меняется с коллекции `TopicPartitionOffset` на `IReadOnlyDictionary<TopicPartition, OffsetAndMetadata>`. Один вызов содержит не более одного значения для раздела темы по форме своего аргумента. Новый тип `OffsetAndMetadata` содержит следующую позицию `Offset`, необязательную эпоху ведущего брокера и пользовательские метаданные смещения. Потребитель должен предоставлять эпоху для прочитанной записи, если она известна, чтобы приложение могло передать её вместе с позицией. Точные значения по умолчанию и проверки полей определяются при реализации контракта; изменение выполняется в рамках шага 06, без заднего изменения уже реализованного шага 01. Перед использованием раздела темы как ключа необходимо исправить `TopicPartition.Equals`: сейчас он сравнивает только хеш-коды, что не гарантирует различения разных разделов.

Согласовано: добавить в `IConsumer` синхронный `ConsumerGroupMetadata GetGroupMetadata()`. Метод без сетевого запроса возвращает согласованный снимок действующего членства: идентификатор группы, поколение и идентификатор участника. Пользователь передаёт этот снимок в существующий `IProducerTransaction.SendOffsetsAsync`; продюсер и потребитель остаются самостоятельными клиентами. Если потребитель ещё не вступил в группу или уже утратил членство, метод завершается ошибкой. Снимок может устареть после возврата метода, поэтому окончательную проверку членства выполняет координатор группы при передаче смещений. Согласованное чтение состояния и ошибка при отсутствии действующего членства требуют отдельной реализации и проверок в потребителе.

Согласовано: на этом этапе поддерживаются только группы с динамическим членством в классическом протоколе `JoinGroup`/`SyncGroup`. В возвращаемом снимке `GroupInstanceId` равен `null`. Постоянное членство и новый протокол групп не объявляются поддержанными в этом шаге. Переход на новый протокол групп Kafka вынесен в [отдельный будущий документ KIP-848](../KIP-848/README.md); это не [новый серверный протокол транзакций](09-server-side-transaction-protocol.md).

Согласовано: одна транзакция может включать смещения нескольких групп потребителей. Для каждой группы приложение отдельно вызывает `SendOffsetsAsync` с её актуальными сведениями о членстве; при хранении принятых смещений ключ включает группу и раздел темы. Подтверждать транзакцию можно только после успешного включения смещений всех участвующих групп с учётом допустимых повторов при временных ошибках. Совместное подтверждение нескольких групп проверяется с настоящим брокером.

Согласовано: при последовательных вызовах `SendOffsetsAsync` позиция одной пары «группа + раздел темы» может остаться прежней или увеличиться. Уменьшение по сравнению с уже принятой в эту транзакцию позицией отклоняется до сетевого запроса; библиотека не подменяет значение максимумом. Для намеренного возврата к более ранней позиции приложение отменяет текущую транзакцию и начинает новую обработку. Внутренний повтор после временной ошибки использует те же смещения и сведения о группе; пока исход предыдущей попытки не определён, новый набор смещений для этой пары не принимается. Проверка не доказывает, что приложение действительно обработало все записи до переданной позиции.

Согласовано: одновременно допускается только один вызов `SendOffsetsAsync` на транзакционном продюсере. Следующий вызов с любым набором смещений, включая пустой, отклоняется до сетевых действий, пока для предыдущего не получен ответ и не завершена его обработка. Отмена ожидания вызывающим кодом сама по себе не освобождает это ограничение: запрос мог уже уйти брокеру. При временной ошибке библиотека разрешает исход либо повторяет прежний запрос с теми же данными; новый набор смещений до завершения этой операции не принимается. Если исход остаётся неизвестным, действуют общие правила завершения транзакции при неизвестном исходе.

Согласовано: если хотя бы одна переданная следующая позиция записи отрицательна, весь вызов `SendOffsetsAsync` завершается ошибкой до сетевых действий. Нулевая позиция допустима. Проверка относится к позициям записей, а не к служебным числовым полям сведений о группе.

Согласовано: при пустом словаре смещений сначала проверяется отсутствие незавершённого предыдущего вызова `SendOffsetsAsync`. Если такой вызов есть, пустой набор отклоняется по общему правилу одновременных вызовов. Иначе метод успешно завершается без сетевых действий; допускается отладочное сообщение об этом пропуске.

Согласовано: если координатор группы отклонил передачу смещений из-за устаревшего поколения или утраты членства, `SendOffsetsAsync` возвращает ошибку, а текущая транзакция переходит в состояние, допускающее только отмену. Библиотека не подставляет новые сведения о группе и не повторяет передачу смещений в той же транзакции: выходные записи могли быть созданы при прежнем владении входными разделами. После отмены приложение заново определяет своё членство и входные позиции перед следующей обработкой.

Согласовано: если после успешного `SendOffsetsAsync`, но до начала `CommitAsync` приложение узнало о потере входного раздела, оно отменяет текущую транзакцию. Автоматическая связь самостоятельных потребителя и продюсера в этом шаге не добавляется; пример должен явно показывать такую проверку. Уже начавшееся подтверждение транзакции нельзя считать отменённым из-за последующей потери раздела: его результат разрешается по общим правилам неизвестного исхода.

Для этих смещений отключается отдельное автоматическое и ручное подтверждение. Библиотека должна явно описать, какие нарушения может проверить локально, а какие остаются обязанностью приложения. Наличие правильного снимка не исключает последующую потерю владения разделами; конечная проверка принадлежит брокеру.

## Валидация и предложенные ограничения

| Вход или событие | Предлагаемое поведение |
|---|---|
| Отрицательная позиция | Согласовано: отказ для всего вызова до сетевых действий |
| Пустой словарь смещений | Согласовано: проверить отсутствие незавершённого предыдущего вызова; затем успех без запроса, допускается отладочное сообщение |
| Вторая группа в той же транзакции | Разрешена; согласованное решение выше |
| Повтор раздела в последовательном вызове | Согласовано: разрешить равную или большую позицию, меньшую отклонить до сетевого запроса |
| Параллельные вызовы включения смещений | Согласовано: второй вызов, в том числе с пустым словарём, отклоняется до сетевых действий, пока не завершена обработка ответа на первый; отмена ожидания не снимает запрет |
| Устаревшее поколение или утрата членства при передаче смещений | Согласовано: ошибка, текущую транзакцию можно только отменить; без автоматической подмены сведений о группе |
| Потеря раздела после успешного `SendOffsetsAsync` | Согласовано: если приложение узнало об этом до начала `CommitAsync`, оно отменяет транзакцию; после начала подтверждения его исход разрешается отдельно |

Несогласованные ограничения таблицы требуют обсуждения. Поля поколения, участника и постоянного членства зависят от выбранной версии и режима группы; нельзя объявлять каждый отрицательный служебный номер невалидным без проверки соответствующего протокола.

## Протокольная последовательность

Определить роли координатора транзакций и координатора группы. В классическом пути включение группы и отправка её смещений выполняются через `AddOffsetsToTxn` и `TxnOffsetCommit`, а окончательная фиксация — через завершение транзакции шага 05. Для иных версий последовательность подтверждается отдельно.

Согласовано: в классическом пути используется `TxnOffsetCommit` версии 3, которая передаёт поколение и идентификатор участника группы, а также необязательную эпоху ведущего брокера. Версии 0–2 не используются: они не передают сведения, необходимые для защиты от устаревшего обработчика. Транзакционный продюсер в целом создаётся только для Kafka 2.5 и новее согласно [шагу 05](05-transaction-protocol-and-lifetime.md); скрытого перехода на старую версию запроса нет. До реализации отдельно проверяется доступность версии 3 на координаторе группы в смешанном кластере.

Обрабатываются ошибки отдельных разделов, повторный поиск обоих координаторов и неизвестный исход. Возврат из `SendOffsetsAsync` означает включение смещений в текущую транзакцию, а не самостоятельную фиксацию группы. `CommitAsync` учитывает все такие принятые операции даже без ожидания их задач приложением.

## Чтение подтверждённых записей

Согласовано: работу транзакционного продюсера в этом шаге проверять независимым потребителем с `read_committed`. Полноценную поддержку `read_committed` в потребителе NKafka проектировать и реализовывать по отдельной спецификации. Для неё необходимо проверить границу стабильных смещений, пропуск записей отменённых транзакций и управляющих записей, а также продвижение позиции через такие пропуски: одно поле настройки изоляции недостаточно. Выпуск сценария «чтение и запись только через NKafka» зависит от завершения этой отдельной работы; успешная проверка продюсера внешним потребителем не подтверждает готовность потребителя NKafka.

Чтение подтверждённых записей не обязано выдавать всю транзакцию за один вызов. Отмена транзакции не возвращает локальную позицию потребителя назад. Приложение повторяет сохранённую порцию либо восстанавливает позиции с учётом текущего владения. Подтверждение смещений Kafka не охватывает отправленные письма, HTTP-запросы и записи во внешнюю базу.

Согласовано: после подтверждённой отмены транзакции пример повторно получает сохранённые смещения для разделов, которыми потребитель всё ещё владеет, и перемещает к ним его позицию перед повторной обработкой. Для потерянных разделов приложение не меняет позицию: дальнейшее чтение выполняет их новый владелец. При неизвестном исходе подтверждения транзакции сначала разрешается этот исход; простой возврат к прежней позиции без этого небезопасен. Необходимые публичные способы получения сохранённых смещений и перемещения позиции потребителя согласовываются отдельно до реализации примера; текущий интерфейс NKafka их не предоставляет.

## Пример, который должен появиться при реализации

Один последовательный обработчик сам создаёт и освобождает транзакционный продюсер. Он читает порцию, получает сведения о группе, начинает транзакцию, отправляет результаты, передаёт следующие позиции и подтверждает транзакцию. При ошибке различает необходимость отмены, окончательную неисправность и неизвестный исход. Общий `singleton` продюсера и автоматическое повторное выполнение функции не используются.

Пример поставляется как компилируемый образец с тестом, английским и русским объяснением. Он должен показывать также восстановление после сбоя и изменение владения разделами, а не только успешный цикл.

## Граничные случаи и проверки

| Момент сбоя | Проверяемый результат после перезапуска |
|---|---|
| До передачи смещений | Незавершённые выходные записи не видны в `read_committed`, вход можно обработать снова |
| После передачи смещений, до подтверждения | Смещения не считаются самостоятельно подтверждёнными |
| После подтверждения на брокере, до ответа приложению | Проверяются и выход, и зафиксированная позиция; нельзя заключать, что операция отменена |
| Перераспределение разделов во время обработки | Устаревший обработчик не фиксирует работу под новым владением |
| Смена координатора группы или транзакций | Допустимый повтор сохраняет атомарность |

Дополнительно проверяются пустые коллекции, неверные позиции, повторные вызовы, частичные ошибки, несколько входных и выходных разделов. Для испытания процесса выполняется настоящий останов и повторный запуск владельца, а не только отмена токена в одной задаче.

## Условия завершения

Смещения и выходные записи проходят совместные испытания с остановкой процесса и перераспределением разделов. Нет ложного успеха `SendOffsetsAsync`. Документирована граница атомарности и требования к потребителю. Публичное дополнение потребителя, если оно необходимо, согласовано отдельно и имеет XML-документацию и тесты.
