# Шаг 08. Обработчики результатов доставки

Статус: черновик для отдельного обсуждения. Документ выделен из шага 03.2, поскольку обработчики доставки образуют самостоятельную подсистему с собственными гарантиями порядка, ограничением ресурсов и правилами остановки.

## Цель и зависимости

Зависимости: шаг 02 определяет `MessageDeliveryResult` и ошибки; шаг 03.2 формирует окончательный исход отправки. Результат шага — безопасная неблокирующая доставка результата в пользовательский `Action`.

## Публичный контракт

Требуется изменить существующий метод `IProducer.Produce`:

```csharp
void Produce(
    TopicPartition topicPartition,
    Message message,
    Action<MessageDeliveryResult> deliveryHandler,
    CancellationToken cancellationToken = default);
```

Второй параметр `Exception?` удаляется. Для каждой принятой записи обработчик получает ровно один окончательный `MessageDeliveryResult`, включая `Error`. Исключения остаются только для ошибок вызова до принятия записи. Обработчик для объекта транзакции этим шагом не добавляется.

## Согласованные правила

- Сетевой цикл формирует результат и передаёт его подсистеме обработчиков; пользовательский `Action` не вызывается в сетевом контексте, под внутренней блокировкой или до освобождения сетевого пути.
- Пользовательские обработчики запускаются через `ThreadPool`, а не на собственных потоках продюсера.
- Исключение из обработчика перехватывается и журналируется. Оно не изменяет результат отправки, не останавливает продюсер и не препятствует обработке других результатов.
- Обработчики одного раздела темы (`TopicPartition` в коде) вызываются в порядке принятия соответствующих сообщений. Между разными разделами порядка не гарантируется.
- Исполнение ограничено: медленный или зависший обработчик занимает только свой слот и не блокирует сетевой путь.
- Произвольный синхронный `Action` нельзя безопасно принудительно остановить. Истечение диагностического срока не означает, что вызов базы данных, файловой системы или внешнего кода действительно завершился.

## Требующие решения вопросы

1. Число одновременно выполняемых обработчиков и настройка этого предела.
2. Предел очереди готовых результатов и его связь с `MaxQueuedMessages` и `BufferMemory`.
3. Алгоритм выбора готового раздела при ограниченном числе слотов.
4. Ожидает ли `FlushAsync` завершения обработчиков или только формирования результатов.
5. Правила `DisposeAsync`: сколько ожидать уже запущенные обработчики, как учитывать не запущенные и что журналировать при истечении срока.
6. Метрики глубины очередей, длительности обработчиков, исключений и занятых слотов.

## Условия завершения

Тестами подтверждены единичный вызов обработчика, порядок внутри раздела, отсутствие выполнения в сетевом контексте, изоляция исключений, ограничение параллелизма и предсказуемое завершение при медленном обработчике и освобождении продюсера.
