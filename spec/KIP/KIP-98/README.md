# KIP-98: продюсеры и транзакции NKafka

## Статус

Начато проектирование. Реализация по этим документам ещё не выполнена.

Согласовано с пользователем:

- Разделить обычный и транзакционный продюсеры.
- Транзакционные сообщения отправляются только через отдельный `IProducerTransaction`; управление транзакцией через неявное состояние общего продюсера не используется в публичном интерфейсе.
- `CreateTransactionalProducerAsync` возвращает `Task<ITransactionalProducer>` и завершает сетевую инициализацию нового экземпляра до возврата; отдельный публичный `InitTransactionsAsync` не нужен.
- Реестр транзакционных продюсеров не создаётся. Каждый успешный вызов создания возвращает новый экземпляр; продюсером и объектом транзакции владеет вызывающий код. Внутри одного `IKafkaCluster` повторное создание активного `TransactionalId` запрещено: ID резервируется до сетевой инициализации и освобождается после полной очистки ресурсов.
- Настройки разделяются на `ProducerConfig` и `TransactionalProducerConfig`. Методы расширения с явным ID формируют конфигурацию и делегируют базовому методу.
- В перегрузках с явным ID отсутствующий ID конфигурации заполняется, совпадающий допускается, а непустой отличающийся вызывает исключение. Исходная конфигурация не изменяется; результат функции настройки проверяется так же.
- `TransactionalProducerConfig` наследует `ProducerConfig` и задаёт корректные транзакционные значения по умолчанию. Если пользователь меняет их на несовместимые, валидатор бросает исключение до сетевой инициализации; настройки не исправляются молча.
- Для продюсеров и объекта транзакции остаётся только `DisposeAsync`, без `IDisposable` и отдельного `CloseAsync`. Вводится отдельная общая опция предельного времени освобождения любого клиента, включая потребителя и административного клиента. Предложенное имя — `ClientDisposeTimeoutMs`; `CloseConnectionTimeoutMs` сохраняет назначение закрытия соединения. Последствия истечения срока обязательно документируются.
- Публичные интерфейсы и связанные типы должны сопровождаться подробной XML-документацией при переносе в исходный код.
- Документация библиотеки создаётся одновременно на английском в `docs/en` и русском в `docs/ru`; английский является базовым языком, структура файлов и разделов одинакова.
- В документации библиотеки обязательно описать опасность регистрации транзакционного продюсера как общего `singleton` в любом контейнере зависимостей и требование явного управления временем жизни из кода. [Руководство по продюсерам](../../../docs/ru/producer/index.md).
- В рамках этой работы упростить публичный интерфейс обычного продюсера.
- Начать со спецификации, без изменения реализации.
- Обратную совместимость текущего публичного интерфейса сохранять не требуется. Устаревшие перегрузки и переходный слой не нужны.
- Последующие изменения описывать отдельными шагами в этой папке.

Остальные сигнатуры в первом шаге и правила поведения в общем замысле являются предложениями для обсуждения. Согласованные решения отмечены явно; реализация контракта ещё не выполнена.

## Назначение

Папка объединяет проектирование и реализацию идемпотентной отправки, транзакционного продюсера и необходимое упрощение обычного продюсера. Название относится к работе NKafka на основе Apache Kafka KIP-98; документы не изменяют сам KIP и не объявляют его поддержку завершённой.

Обычный продюсер отправляет сообщения без объединения в транзакцию. Идемпотентная отправка может быть доступна ему независимо от транзакций. Транзакционный продюсер управляет транзакциями, а отправка сообщений выполняется через объект конкретной транзакции.

## Границы

В работу входят:

- Публичные интерфейсы, создание клиентов, настройки, результаты и ошибки.
- Владение ресурсами, ограничение памяти и завершение работы.
- Накопление и сериализация пакетов, повторные отправки и порядок записей.
- Идемпотентность, идентификатор продюсера, эпохи и последовательности.
- Начало, подтверждение и отмена транзакции, восстановление после ошибок.
- Включение смещений потребителя в транзакцию.
- Проверки совместимости с брокером, испытания со сбоями и измерения производительности.
- Изменение затронутых примеров, регистрации клиентов в приложении и документации.

В эту работу не входят распределённые транзакции с базами данных и внешними службами, транзакции между Kafka-кластерами, реализация Kafka Streams и полная переработка потребителя. Изменения потребителя, необходимые для получения сведений о группе и проверки чтения подтверждённых записей, описываются явно в соответствующем шаге.
