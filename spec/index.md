# Базовая спецификация NKafka

## Назначение документа

Этот файл является базовой спецификацией `NKafka` и должен использоваться как основной design document после чтения [AGENTS.md](K:\nkafka\AGENTS.md).

Если при реализации возникает неопределенность, порядок чтения контекста должен быть таким:

1. [AGENTS.md](K:\nkafka\AGENTS.md).
2. Этот файл.
3. [spec/technical-requirements.md](K:\nkafka\spec\technical-requirements.md).
4. Специализированные документы из `spec/`, включая KIP-аналитику.
5. Исходный код, тесты и JSON-спецификации сообщений.
6. Официальные спецификации Kafka и соответствующие KIP.

## Источники истины

Для проектных решений приоритет источников должен быть следующим:

1. Код и контракт `NKafka`.
2. [AGENTS.md](K:\nkafka\AGENTS.md) как project context.
3. [spec/technical-requirements.md](K:\nkafka\spec\technical-requirements.md) как project-level technical requirements.
4. Официальные Kafka protocol/message definitions из `resources/message/` и `kafka/`.
5. Тесты как исполняемая спецификация поведения.
6. Документация в `docs/`, `README.md` и `spec/`.

Если источники конфликтуют:

- generated-код не редактируется вручную
- message wire contract определяется спецификацией Kafka
- пользовательское поведение библиотеки должно подтверждаться тестами
- архитектурные и процессные правила берутся из `AGENTS.md`

## Цель библиотеки

`NKafka` — это высокопроизводительный fully managed Kafka client для .NET без зависимости от `librdkafka`.

Библиотека должна:

- нативно реализовывать Kafka protocol на C#
- предоставлять producer / consumer / admin API
- быть предсказуемой по ресурсам
- минимизировать лишние соединения и аллокации
- поддерживать observability
- оставаться совместимой с современными версиями Kafka

## Область ответственности

В базовую область ответственности клиента входят:

- подключение к Kafka cluster через bootstrap servers
- discovery и обновление metadata
- producer API
- consumer API и group management
- admin operations
- client-side security: SSL, SASL, OAuth
- сериализация и десериализация Kafka protocol messages
- диагностика, telemetry и client metrics

Не входят в базовую область ответственности:

- broker-side логика
- KRaft/controller internals без client impact
- Kafka Connect runtime
- Kafka Streams runtime
- ручное редактирование generated protocol classes

## Архитектурные принципы

### Cluster-first design

Центральной точкой входа является cluster abstraction.

Именно cluster:

- хранит базовую конфигурацию подключения
- управляет metadata
- предоставляет factory для producer / consumer / admin clients
- владеет общими сетевыми ресурсами

Все клиенты должны рассматриваться как производные от cluster context.

### High-performance by default

Любые решения в hot path должны оцениваться с учетом:

- количества аллокаций
- копирования памяти
- лишних сериализаций
- числа сетевых round-trip
- количества соединений
- количества фоновых потоков и задач

Предпочтение должно отдаваться:

- `Span<T>` / `Memory<T>`
- `System.IO.Pipelines`
- повторному использованию буферов и объектов там, где это безопасно
- version-aware protocol handling без лишней абстракции в hot path

### Минимизация соединений

Библиотека должна избегать лишних физических соединений.

Базовые правила:

- producer-oriented операции по возможности используют общие cluster-level connections
- consumer использует выделенное соединение там, где этого требует модель Kafka
- новые соединения создаются только когда это оправдано протоколом или производительностью

### Protocol-first implementation

Реализация должна строиться вокруг официального Kafka protocol.

Это означает:

- version-aware обработку API
- аккуратную работу с `ApiVersions`
- поддержку flexible versions и tagged fields
- реализацию новых KIP-ов через изменение protocol/message contracts

### Explicit compatibility

Поддержка возможностей Kafka должна быть явной.

Если feature зависит от:

- версии broker
- версии API
- feature flag
- KIP-specific protocol revision

то это должно быть отражено в коде, тестах и документации.

## Правила работы с protocol messages

### Generated code

Файлы `*.g.cs` не редактируются вручную.

Если требуется изменить generated message behavior:

- меняется message specification
- либо добавляется `partial class` в отдельном ручном файле
- тесты для autogenerated artifacts по умолчанию тоже должны генерироваться или поддерживаться через generator-driven подход

### Message specifications

Основной источник message schema:

- `resources/message/*.json`
- при необходимости официальные Kafka definitions из `kafka/`

Базовый принцип:

- генерация message contracts должна оставаться согласованной с reference-моделью Kafka/Java
- этот baseline нужно поддерживать отдельно и обновлять по мере изменения protocol specs
- локальные изменения генерации не должны случайно отрывать `NKafka` от reference contract behavior

Изменения в message contracts должны сопровождаться:

- проверкой версий запроса и ответа
- проверкой nullable/flexible/tagged semantics
- проверкой backward/forward compatibility

### Версионность

Каждое protocol change должно оцениваться через:

- минимальную поддерживаемую версию API
- максимальную доступную версию API
- поведение на старых broker versions
- fallback path, если feature не поддерживается

## Правила разработки API клиента

Публичный API `NKafka` должен быть:

- понятным для .NET-разработчика
- безопасным по умолчанию
- асинхронным там, где идет I/O
- согласованным между producer / consumer / admin layers

При проектировании API нужно избегать:

- утечек низкоуровневых protocol details в пользовательский API без необходимости
- скрытых blocking операций
- неявных тяжелых фоновых действий
- зависимостей от нативных компонентов

## Подход к KIP-ам

KIP должен попадать в roadmap клиента только если он:

- меняет client protocol behavior
- добавляет client-visible API или semantics
- влияет на producer / consumer / admin / security / telemetry behavior

Для современного roadmap приоритетнее KIP-ы для Kafka `>= 2.0`.

## Качество и инженерные правила

### Язык и платформа

- основной язык: `C#`
- целевые платформы: `.NET 8.0` и `.NET 9.0`
- nullable reference types должны соблюдаться строго
- допускается `unsafe`, если это оправдано производительностью
- код должен писаться с учетом AOT compilation
- должны использоваться современные возможности языка, если они не конфликтуют с AOT и требованиями проекта

### Code style и tooling

- `.editorconfig` является обязательным источником правил code style и analyzer expectations
- новый и изменяемый код не должен оформляться вразрез с [.editorconfig](K:\nkafka\.editorconfig)

### Статический анализ

Проект использует `PVS-Studio`.

Для новых ручных файлов нужно:

- соблюдать стиль проекта
- добавлять требуемый PVS-Studio header в C# файлы
- не указывать версии пакетов в `.csproj`, если пакет управляется централизованно

### Тестирование

Любое заметное изменение должно сопровождаться подходящими тестами:

- unit tests для локальной логики
- integration tests для cluster/protocol behavior
- generator tests для message-generation сценариев
- для каждого изменяемого модуля требуется unit-test покрытие
- для autogenerated файлов тесты по умолчанию тоже должны быть autogenerated или generator-driven

Если change затрагивает performance-sensitive path, нужно дополнительно оценить влияние на `benchmarks/`.

### Комментарии, логи и локализация

- комментарии и log messages внутри библиотеки по умолчанию пишутся на английском языке
- для сообщений, которые должны поддерживать локализацию или уже следуют локализуемому шаблону проекта, должны использоваться resource files

## Рабочий процесс изменений

При реализации изменений рекомендуется следовать такой последовательности:

1. Определить feature / bug / KIP / protocol gap.
2. Проверить, затрагивает ли это generated messages, ручной код, API или tests.
3. Найти соответствующую Kafka specification и версионные ограничения.
4. Внести минимально необходимое изменение.
5. Подтвердить поведение тестами.
6. При необходимости обновить `spec/`.

## Структура проекта

Ключевые директории:

- `src/NKafka` — основная библиотека
- `src/NKafka.MessageGenerator` — генератор message classes
- `resources/message` — message specifications
- `tests` — unit и integration tests
- `benchmarks` — performance verification
- `samples` — usage examples
- `kafka` — reference repository/spec context
- `spec` — проектные спецификации и аналитические материалы

## Что считать завершенным изменением

Изменение считается базово завершенным, если:

- код реализован
- не нарушены project rules из [AGENTS.md](K:\nkafka\AGENTS.md)
- generated code не редактировался вручную
- добавлены или обновлены тесты, если это требуется
- обновлена спецификация, если изменилась архитектура, поведение или roadmap

## Роль этого файла

Этот документ не заменяет код, тесты и Kafka protocol definitions.

Его задача:

- фиксировать базовые принципы разработки клиента
- задавать единый vocabulary для проектных решений
- быть главным базовым spec-документом внутри `spec/`
- снижать неоднозначность при работе над producer, consumer, admin и protocol layers
