# Технические требования NKafka

## Project Overview

NKafka is a high-performance, fully managed Kafka client for .NET, written in C#. It aims to provide a native .NET implementation of the Kafka
protocol without relying on native librdkafka.

- **Primary Language**: C# 13
- **Target Frameworks**: .NET 8.0, .NET 9.0
- **Key Features**: High performance, OpenTelemetry support, centralized package management.

## Project Structure

- `src/NKafka`: The core library containing the Kafka client implementation.
    - `Clients/`: Producer and Consumer implementations.
    - `Protocol/`: Kafka protocol implementation, including serialization and primitives.
    - `Messages/`: Generated and manual Kafka protocol message classes.
    - `Serialization/`: Built-in serializers and deserializers.
- `src/NKafka.MessageGenerator`: A tool that generates C# code for Kafka protocol messages from JSON specifications.
- `kafka/`: A submodule or directory containing the official Apache Kafka repository, used for protocol specifications.
- `tests/`: Unit and integration tests using xUnit and FluentAssertions.
- `benchmarks/`: Performance benchmarks using BenchmarkDotNet.
- `samples/`: Example usage of the library.

## Coding Guidelines

### Code Generation

- **DO NOT** manually edit files with the `.g.cs` extension. These are generated by `NKafka.MessageGenerator`.
- To extend a generated message, use `partial class` in a separate `.cs` file within the same namespace.
- Message specifications are typically derived from the official Kafka JSON definitions found in the `kafka` directory.
- Tests for autogenerated files must also be autogenerated where possible.
- If a generated protocol/message artifact changes, its generated or generation-driven tests must be updated together with it.

### Reference Contract Generation Baseline

- The project keeps the message-contract generation baseline aligned with the reference Kafka definitions and generation model coming from the Java reference implementation.
- This baseline must be treated as a separately maintained compatibility layer, not as an ad-hoc part of ordinary feature work.
- Changes to generated message contracts should follow the reference Java/Kafka definitions first, and only then be adapted to the NKafka generator model.
- Any divergence from the reference contract-generation behavior must be intentional, documented, and justified.
- The reference-aligned generation baseline should be reviewed and updated separately when Kafka protocol specs, message definitions, or generation assumptions evolve.

### C# Language Features

- Use the latest C# 13 features where appropriate:
    - Primary constructors.
    - Collection expressions (`[...]`).
    - `ref readonly` and other performance-oriented features.
- Prefer modern language/runtime patterns when they improve clarity, safety, or performance and do not conflict with AOT requirements.
- The project allows `unsafe` code for performance optimizations.

### AOT Compatibility

- New code must be written with Native AOT compatibility in mind.
- Avoid runtime patterns that rely on unrestricted reflection, dynamic code generation, or non-trimmable implicit discovery unless there is a documented and tested reason.
- Public and internal APIs should prefer static, analyzable code paths.
- If reflection or runtime activation is required, the reason and compatibility implications must be explicit.

### Logging, Comments, and Localization

- Comments and log messages inside the library are written in English by default.
- User-visible or reusable log/error text should use resource files where localization is expected.
- New hardcoded strings in library internals should be avoided when an existing resource-based pattern is already used for the same category of messages.

### Code Style

- The repository uses [.editorconfig](K:\nkafka\.editorconfig) as the source of truth for code style and related analyzer requirements.
- New and modified code must follow `.editorconfig` rules instead of local/editor defaults.

### Static Analysis and Quality

- The project uses **PVS-Studio** for static analysis. Include the PVS-Studio header in new manual files.
- **Nullable Reference Types** are enabled and should be strictly followed.

### Centralized Package Management

- Package versions are managed centrally in `Directory.Packages.props`. Do not specify versions in `.csproj` files.

## Development Workflow

1. **Initialize/Update**: Run `update_repo.ps1` (Windows) or `update_repo.sh` (Linux) to sync submodules and tools.
2. **Build**: Use `dotnet build` from the root directory.
3. **Generate Messages**: If protocol specifications change, run the `NKafka.MessageGenerator` tool.
4. **Test**: Use `dotnet test` to run all tests. Ensure that all tests pass before submitting changes.

## Testing Requirements

- Every module change must be accompanied by unit tests for the affected logic.
- Autogenerated files must have autogenerated or generator-driven tests as the default testing strategy.
- Manual code around generated artifacts should also be covered when behavior is added outside the generator.
- Integration tests are required when the change affects broker interaction, protocol negotiation, security, metadata flow, group coordination, or transaction semantics.
- If a change cannot reasonably be covered by tests, the gap must be explicit in the change description or spec update.

## Protocol Implementation

- Kafka messages are implemented using `IRequestMessage` and `IResponseMessage` interfaces.
- Each message version is handled via a `Version` property.
- Pay attention to `ApiVersion` when implementing or extending message logic.

## Performance Considerations

- NKafka is designed for high performance. Avoid unnecessary allocations in the hot path.
- Use `System.IO.Pipelines` and `Span<T>`/`Memory<T>` where appropriate.
- Monitor `benchmarks/` when making changes to the data path.
